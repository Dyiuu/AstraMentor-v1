# 项目6：实现受控的单轮函数与工具调用

## 岗位情境

教务问答页面需要查询公开课程安排。原型把 `get_schedule` 描述交给模型，收到工具名和参数后直接用反射调用同名 Python 函数。一次输入让模型提交了不存在的课程 ID，另一次请求了开发者调试函数；日志把“模型已请求”写成“查询已完成”，即使数据库根本没有执行。你要实现一个受控单轮工具网关：模型只能从白名单提出调用，应用验证参数、权限和结果，再把真实结果回传模型形成最终答复。

这里的“单轮”是一次用户请求最多处理一批明确工具调用和一次结果总结，不实现自主循环、规划或多 Agent。任何写入、付款、发信等有副作用工具都不在本项目自动执行范围。

## 项目目标

- 能说明工具 Schema 是提供给模型的选择说明，不是可执行权限。
- 能定义窄职责函数、JSON Schema 参数和稳定结果契约。
- 能校验工具名、参数类型、业务范围、调用者权限和超时，再由应用显式执行。
- 能用 `tool_call_id` 将真实工具结果与请求对应，并区分 requested、approved、executed、failed 状态。
- 能处理未知工具、畸形参数、无权限、超时和结果过大，完成可重复的离线测试。

## 项目产物与验收条件

产物为只读课程查询工具、工具注册表、执行审计事件和单轮编排函数。

- [ ] 输入用户问题与两个允许工具定义，输出最终自然语言或明确失败，不调用注册表之外的函数。
- [ ] 参数先经过 Pydantic 与业务规则校验；课程 ID 必须属于调用者可访问范围。
- [ ] 每次状态转换带 trace_id 与 tool_call_id，只有函数成功返回后才出现 `executed`。
- [ ] 工具结果截断并结构化，模型返回内容永远不能伪装为真实执行日志。
- [ ] 验收证据包含五种响应桩、工具调用计数、审计事件、权限测试和无副作用声明。

## 任务分析

### 岗位任务、输入与输出

输入是用户问题、身份上下文、允许工具 Schema 和模型返回的零个或多个 tool_calls；中间输出是待审批调用；执行输出是由本地函数产生的结构化结果；最终输出是模型基于这些真实结果生成的说明。关键责任分离为“模型建议工具”和“应用决定并执行工具”，不能让模型生成的函数名直接进入 `globals()` 或 shell。

可复现实训建立内存课程表，工具响应固定且无网络副作用。模型用桩依次返回无工具、合法查询、未知工具、错误类型、越权课程和超长结果。测试断言实际函数调用次数与审计状态，任何拒绝场景的调用次数必须为零。

## 核心知识

### 工具调用是协议，不是远程代码执行

兼容接口中的工具定义通常包含名称、描述和 JSON Schema 参数。模型响应的 tool_calls 只是结构化建议；官方文档明确说明应用在客户端单独执行，再把结果作为 `role=tool` 消息回传。开发者必须把模型当不受信任的调用者：工具名走固定映射，参数走解析与业务校验，身份和授权来自服务端会话而不是模型参数。

### 工具契约应窄而可验证

`get_schedule(course_id, date)` 比 `run_query(sql)` 更适合开放给模型，因为参数空间和权限容易说明。Schema 描述用于帮助模型选择，服务端 Pydantic 才是强制边界。工具结果应包含状态、公开数据和可展示错误，不返回数据库对象、堆栈或内部凭据。超长结果先由工具层分页或裁剪，避免重新塞满上下文。

### 状态与幂等性

一次调用至少经历 requested、validated、authorized、executed/failed。模型输出不能直接创建 executed 事件。只读查询可安全地在受控暂态故障下重试；有副作用操作需要幂等键、明确确认和更严格审计，留到 Agent 与生产安全课程深入。并行 tool_calls 也必须逐个校验，本项目可以按固定顺序执行以简化审计。

## 工程实现步骤

1. 选择只读公开课程表场景，写出工具用途、非用途、参数、返回、权限、超时和最大结果数。
2. 定义 Pydantic 参数模型，并生成 `additionalProperties: false` 的 Schema；描述中不给模型任何内部实现细节。
3. 建立不可变注册表 `{"get_schedule": ToolSpec(...)}`，禁止动态导入、反射和任意 URL。
4. 第一次模型请求携带工具定义。若没有 tool_calls，直接校验普通回答；若有则逐项保存 requested 事件。
5. 校验 tool_call_id、白名单名称和 JSON 参数；从认证上下文检查 course_id 权限，不能信任参数内的 user_id。
6. 在超时和结果上限内调用函数；成功后才写 executed，并以同一 tool_call_id 构造 tool 消息。失败写安全错误，不把堆栈给模型。
7. 第二次模型请求只要求依据工具结果总结并引用查询日期；若再次提出工具，按单轮边界返回需要新请求。
8. 用六类桩运行测试，审阅实际调用计数、状态顺序、日志脱敏和最终输出。

## 关键代码与配置

执行器只从注册表取函数，身份授权在调用前独立完成。

```python
import json
from pydantic import BaseModel

class ScheduleArgs(BaseModel):
    course_id: str
    date: str

TOOLS = {"get_schedule": get_schedule}

def execute(call: dict, allowed_courses: set[str]) -> dict:
    name = call["function"]["name"]
    if name not in TOOLS:
        raise ValueError("工具不在允许列表")
    args = ScheduleArgs.model_validate_json(call["function"]["arguments"])
    if args.course_id not in allowed_courses:
        raise PermissionError("无权查询该课程")
    return TOOLS[name](args.course_id, args.date)
```

## 调试和常见故障

### 故障案例一：未知工具名触发任意函数

- **现象：** 测试桩返回 `debug_dump`，旧代码通过 `globals()[name]` 找到并执行了内部函数。
- **原因：** 把模型生成的名称当作可信代码符号，没有工具注册表和最小暴露面。
- **定位：** 搜索动态反射调用，使用未知名称运行测试并统计内部函数是否被触发。
- **修复：** 仅允许固定注册表映射；未知名称在执行前拒绝并记录 failed，测试断言实际调用数为零。

### 故障案例二：审计显示成功但数据库未查询

- **现象：** 页面显示“课程表查询已完成”，工具日志没有结果，实际函数因超时抛出异常。
- **原因：** 收到 tool_calls 时就写 `executed=true`，混淆模型请求与应用执行。
- **定位：** 按 tool_call_id 排列事件，发现 requested 后没有函数完成事件却已有 executed。
- **修复：** 使用状态机；只有函数正常返回并通过结果校验后写 executed，异常写 failed，最终回答明确查询未完成。

### 故障案例三：参数类型正确但发生越权查询

- **现象：** `course_id` 是合法字符串，模型却查询到了当前教师无权访问的课程。
- **原因：** Pydantic 只验证结构，应用没有用服务端身份检查资源范围。
- **定位：** 用两个不同权限身份提交同一参数，查看授权逻辑是否错误地读取模型传入的 user_id。
- **修复：** 身份只来自已验证会话，按 allowed_courses 做对象级授权；拒绝事件不得包含受限课程详情。

## 安全、成本与职业规范提示

工具会把自然语言影响扩展到真实系统，因此必须最小权限、参数白名单、对象级授权、限时和审计。本项目只开放只读内存查询。涉及写入、发送消息、购买或设备控制时，必须有明确的人类确认、幂等设计和补偿方案，不能照搬当前自动执行流程。工具结果也可能包含提示注入文本，应视为数据而不是新系统指令。

工具调用通常需要至少两次模型请求，成本与延迟要单独记录。结果应分页、过滤不需要字段，并缓存可公开的稳定查询。职业报告须用 requested/validated/executed 等准确术语，不可为了展示效果把模型“想调用”描述成真实完成，也不能隐瞒失败或权限拒绝。

## 实训练习

1. 为 `get_schedule` 写工具卡片和 JSON Schema，列出两个明确非用途以及返回字段上限。
2. 使用六种模型桩运行单轮编排，断言未知、畸形和越权场景的函数调用次数为零。

## 本项目小结

函数调用把模型的结构化建议接入应用能力，但权限始终掌握在应用端。固定注册表、严格参数、服务端身份、状态机和真实结果回传构成最小可信链。本项目以只读、单轮和离线桩限制风险，也明确了 requested 与 executed 的职业表达。下一项目将集中解决流式首字延迟、取消、断线与降级，不扩大工具自主性。
