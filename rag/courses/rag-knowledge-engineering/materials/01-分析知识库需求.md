# 项目1：分析可评测的知识库需求

## 岗位情境

学院准备建设“实训安全规范知识助手”。需求会上有人提出“把全部文件放进去，回答准确率达到 95%”，却没有说明谁提问、哪些文件有效、旧制度如何处理、什么叫准确。试做系统对“焊接实训进入工位前要检查什么”给出流畅答案，但引用的是已废止版本。你作为 RAG 工程师，需要先把模糊愿望转化为可检索问题、文档边界、权限、拒答规则、服务指标和验收问题集。

本项目不编写切分或向量代码。需求基线将约束后续文档、索引、检索、生成和评测；若基线含糊，优化模型只会更快地产生不可验收结果。

## 项目目标

- 能识别知识助手的用户角色、岗位任务、问题类型和决策风险。
- 能建立权威来源、时效、版本、权限与排除项明确的语料范围。
- 能把“准确”拆为检索证据、答案依据、引用可追溯、拒答和时延指标。
- 能创建覆盖常见、长尾、歧义、越界和过期冲突的代表性问题集。
- 能提交需求基线与验收矩阵，使文档和算法岗位按同一目标协作。

## 项目产物与验收条件

产物为一份知识库需求说明、来源登记表、20 条首版问题集和风险分级表。输入为岗位目标、用户问法、来源目录、权限和更新流程；输出为已签收的语料边界、结构化问题集与指标口径；验收证据按下列清单归档。

- [ ] 每个用户故事写清角色、触发问题、需要的证据、允许动作和失败影响。
- [ ] 语料清单标记负责人、适用范围、生效/失效日期、版本、权限和更新频率。
- [ ] 20 条问题至少包含 8 条直接事实、4 条步骤、3 条对比、2 条歧义、2 条越界和 1 条版本冲突。
- [ ] 每条可回答问题关联预期来源与证据位置；越界问题定义期望拒答及下一步提示。
- [ ] 验收证据包含访谈记录摘要、批准的范围、问题集版本、风险签字和指标计算说明。

## 任务分析

### 岗位任务、输入与输出

输入是业务目标、现有文档目录、用户角色、真实问法样本、权限规则、更新流程和性能预算；输出是可实现、可测量、可签收的 RAG 需求基线。问题集不是关键词清单，而是包含 query、intent、answerability、expected_sources、evidence、risk、access_role 和备注的结构化资产。

可复现实训使用课程内自编的五份“安全规范”小文档，其中安排当前版、旧版、常见问题、无关制度和受限附件。学生先独立标注 20 问，再与同伴交叉审阅分歧。后续项目使用同一版本问题集，因此每次改动要保存 changelog，不能为迎合当前检索结果随意修改答案。

## 核心知识

### RAG 需求围绕证据链

检索增强生成的基本思想是先从外部语料取回相关证据，再让生成模型结合证据作答。工程目标不是“模型知道更多”，而是对特定问题找到允许使用的材料、形成有依据回答并能指回来源。原始 RAG 研究区分参数化知识与外部非参数化记忆，实际职业项目还必须补充版本、权限、时效和引用位置。

### 可回答性和拒答

一个问题可能在范围内但材料没有答案，也可能有答案但当前用户无权访问，还可能因时间或对象歧义无法确定。需求中要定义 `answerable`、`insufficient_evidence`、`ambiguous`、`out_of_scope`、`forbidden` 等结果。拒答不是系统失败；在安全规范场景，基于不足证据给出具体步骤才是高风险失败。拒答还需提供可行动的澄清问题或权威联系渠道。

### 指标分层

端到端答案评价不能定位问题。需求至少拆成：检索层的 Recall@K（预期证据是否进入前 K）、来源权限合规率；生成层的依据一致性、问题相关性、引用精确性和拒答正确率；服务层的 P95 延迟、可用性和单位查询成本。阈值依据风险与基线数据确定，不应在没有样本时承诺一个漂亮百分比。

### 问题集要防止数据偏见

若问题全部复制文档标题，关键词检索会显得异常优秀。真实用户会使用简称、口语、错别字、跨章节问题和含糊时间。问题集应保留自然表达，并让文档维护者与一线用户共同标注。测试集与调参集分开，最终验收问题在定版后冻结，避免持续“改题迎合系统”。

## 工程实现步骤

1. 访谈一线学生、教师、文档负责人和数据安全人员，记录他们完成什么任务以及错误答案的实际影响。
2. 对问题按事实、步骤、条件、比较、汇总和不可回答分类；为高风险类规定必须命中的来源与人工出口。
3. 建立语料来源登记：文档 ID、标题、发布单位、版本、生效状态、权限、许可、更新负责人和原始位置。
4. 写入明确排除项，如学生成绩、个人联系方式、未批准草稿、失效制度和开放网页全量抓取。
5. 定义结果状态和拒答文案原则；对歧义问题先要求补充设备型号、课程或日期。
6. 编制 20 问 JSONL，为每条可回答问题标注一到多个证据片段 ID，不把答案原句硬塞进查询。
7. 两名标注者独立检查 answerability 和来源，记录分歧并由文档负责人裁决，形成版本 1.0。
8. 建立指标公式、调参/验收划分和变更审批。需求基线由业务、内容与技术三方签收。

## 关键代码与配置

问题集使用机器可读字段，便于后续检索与端到端评测复用。

```json
{
  "id": "safety-014",
  "query": "进入焊接工位前要做哪些检查？",
  "intent": "procedure",
  "answerability": "answerable",
  "expected_sources": ["safety-rule-2026"],
  "evidence_ids": ["safety-rule-2026#2.1"],
  "risk": "high",
  "access_role": "student"
}
```

```python
def recall_at_k(result_ids: list[str], expected: set[str], k: int) -> float:
    if not expected:
        raise ValueError("可回答问题必须标注预期证据")
    found = expected.intersection(result_ids[:k])
    return len(found) / len(expected)
```

## 调试和常见故障

### 故障案例一：验收准确率很高，真实问法却检索不到

- **现象：** 内部 20 问达到目标，上线后学生使用简称和口语时频繁拒答。
- **原因：** 测试问题由文档维护者直接复制标题，缺少真实角色表达和长尾类型。
- **定位：** 比较验收 query 与匿名化真实 query 的词汇重合、长度和问题类型分布，发现明显偏差。
- **修复：** 让一线用户提供脱敏问法，按类型分层抽样；冻结独立验收集，调参只使用开发集。

### 故障案例二：系统引用已废止规范

- **现象：** 答案证据文字完全匹配，但来源版本去年失效，当前版要求不同。
- **原因：** 语料清单没有生效状态和时间过滤，团队把“文件存在”当“可用来源”。
- **定位：** 追溯引用的 document_id、版本与 effective_to，检查检索需求是否定义当前时间过滤。
- **修复：** 来源登记强制版本和生效字段；默认只检索当前有效材料，历史比较必须由明确问题触发并标注旧版。

### 故障案例三：无法回答被统计为错误

- **现象：** 团队为了提高表面准确率，模型对范围外的设备维修问题也给出步骤。
- **原因：** 指标只计算“是否给出答案”，没有拒答正确率和风险分级。
- **定位：** 审查问题集的 answerability 分布，确认没有越界或材料缺失样例。
- **修复：** 增加越界、歧义和权限样例，单独计算正确拒答；高风险错误回答设为发布阻断项。

## 安全、成本与职业规范提示

需求阶段就应遵循数据最小化。不要因为“以后可能有用”把成绩、联系方式或未授权内部附件纳入语料。来源负责人要确认版权或使用许可，搜索结果必须执行当前用户权限，不能靠生成模型提示隐藏受限内容。高风险操作步骤应显示适用版本和人工确认渠道。

评测和访谈记录也可能包含敏感问题，应脱敏、限权和设定留存。性能与成本目标要与风险目标共同签收：节省一次检索不能成为跳过权限过滤或证据核验的理由。岗位报告应把未知和假设明确列出，不编造尚未测得的阈值。

## 实训练习

1. 为安全规范助手写四类用户故事，每类说明证据、权限、失败影响和人工出口。
2. 建立五份样例文档的来源登记，特意加入一个旧版和一个受限文件，写出默认过滤规则。
3. 编制 20 条自然问题并交叉标注；计算两人对 answerability 的一致数量，记录并裁决分歧。
4. 为检索、答案、引用、拒答和服务层各定义至少一个可计算指标，说明阈值需要什么基线数据。
5. 提交版本化 JSONL、批准范围、排除项和复现校验命令；验收者随机抽三问核对证据位置。

## 学习评价量表

| 评价维度 | 权重 | 合格表现 | 优秀表现 |
|---|---:|---|---|

总分达到 60 分为合格；未定义语料版本、权限或正确拒答时，即使总分达到阈值也需整改。

## 本项目小结

RAG 工程从可评测需求开始。用户任务决定问题类型，权威语料决定证据边界，风险决定拒答与人工出口，问题集和分层指标决定系统能否被客观验收。把版本、权限和时效写进基线，可以防止“检索到旧文档也算成功”。下一项目将把批准语料转换为标准化、可追溯的 Document 数据。
