# 项目七：构建多智能体系统

## 岗位情境

学校准备上线面向实习生的求职训练服务：需求分析助手负责澄清岗位方向，课程顾问负责匹配学习资源，简历教练负责检查材料，安全审核员负责发现隐私与夸大描述。单个 Agent 的提示越来越长，工具权限也难以隔离。团队希望你把业务拆成可协作的多个专业 Agent，同时避免循环移交、意见冲突和责任不清。

多智能体不是把同一个模型复制几份。每个角色需要清楚的输入、输出、工具和停止边界；编排器决定何时路由、并行、汇总或转人工。若一个确定性函数就能完成分类，就不应为了“看起来智能”增加 Agent。本项目以可测试的求职训练流程验证拆分是否真正提升质量与治理能力。

## 项目目标

完成后，你能够根据能力、权限和上下文边界判断是否采用多智能体；设计管理者集中编排和去中心化 handoff 两种模式；定义可验证的移交契约；解决并行结果冲突、超时、重复工作和循环路由；构建全局追踪与预算；并用单 Agent 基线证明方案的收益。

课程强调“最少必要角色”。最终系统包含三个业务角色和一个安全审核角色，但只有编排器持有全局状态；子 Agent 只能看到完成任务所需的上下文与工具。

## 项目产物与验收条件

- 输入：求职训练用户故事、角色权限表、课程查询和材料检查工具、十组代表性任务。
- 输出：协作拓扑、角色卡、handoff Schema、编排代码、冲突策略、预算策略和对比评测报告。
- 验收证据：五类任务路由正确；子角色不能越权调用其他工具；移交不丢失目标与证据；循环在阈值内停止；并行超时可降级；多智能体相对基线的改进有量化依据。

| 验收项 | 通过标准 | 证据形式 |
|---|---|---|
| 角色边界 | 每个角色目标、工具和禁区明确 | 角色卡与权限测试 |
| 路由移交 | 原因、上下文摘要和期望输出完整 | handoff 事件样例 |
| 冲突处理 | 规则可复现且保留异议 | 冲突测试记录 |
| 运行控制 | 循环、超时与总预算受限 | 压力测试时间线 |
| 方案价值 | 与单 Agent 基线同集评测 | 对比报告 |

## 任务分析

第一步不是写提示词，而是分析耦合：课程顾问需要只读课程检索，简历教练需要材料解析，安全审核员只需读取候选结果而不应修改原文。它们的工具与规则差异足够大，适合拆分。常规字段检查和预算计算仍由确定性代码完成。

选择管理者模式时，中心编排器保留用户会话，子 Agent 返回结构化建议，适用于严格控制和集中汇总。选择 handoff 模式时，当前 Agent 把会话控制权连同上下文摘要移交给另一角色，适合需要连续追问的专业阶段。无论哪种模式，都必须限制移交次数并记录责任链。

## 核心知识

### 拆分依据与协调成本

角色拆分的合理依据包括不同专业指令、不同工具权限、不同数据作用域或可独立评测的子任务。每增加一个 Agent，就增加一次模型调用、上下文转换和失败点。若角色经常需要共享全部历史，拆分可能只带来成本与信息损失。工程评审应记录为什么普通函数或单 Agent 不够。

### 管理者与去中心化移交

管理者模式由中心节点选择子 Agent，子结果回到中心统一合成，便于预算和安全策略集中执行。去中心化模式允许角色之间 handoff，下一角色接管对话，更自然但更容易形成环。混合模式可以让管理者决定大阶段，在阶段内部允许一次受控移交。

### 移交契约

Handoff 不是一句“请你继续”。结构化载荷应包含 task_id、目标、已确认事实、证据引用、未解决问题、建议接收角色、移交原因、期望产物和剩余预算。接收者首先验证自己是否具备能力；不具备时返回拒绝原因，而不是继续把任务踢走。敏感原文仅在接收者确有权限时传递。

### 冲突与聚合

并行角色可能产生不一致建议。数值或规则结论可由确定性验证器裁决；需要判断的内容可交给有明确量表的审核角色，但审核者必须看到证据而非只看结论。聚合器保留异议、置信信息和来源，不把多数票当成事实。涉及用户偏好的冲突应展示选项并让用户决定。

### 全局状态与可观测性

每次调用有 trace_id，全局任务有 run_id，子 Agent 有 span 和 parent_span。状态机记录当前所有者、移交计数、已用 Token、截止时间和已产生产物。日志展示“谁基于什么证据做了什么决定”，同时对个人简历内容脱敏。终止条件由全局编排器执行，不能分散在提示中。

## 工程实现步骤

### 步骤一：建立单 Agent 基线

先用一个受控 Agent 运行十组任务，记录正确率、平均延迟、Token、越权次数和人工评分。把失败归因到提示冲突、工具误用或专业不足；只有拆分能针对性解决的失败才进入多角色设计。

### 步骤二：定义角色卡和权限矩阵

为每个角色写明职责、非职责、输入 Schema、输出 Schema、允许工具、可见数据和升级条件。注册工具时按角色创建独立集合。安全审核员可以标注风险，但不能直接提交或修改用户材料。

### 步骤三：实现路由与移交

用规则优先处理清晰意图，不确定时再调用路由模型。编排器验证 handoff 载荷，更新当前所有者和剩余预算。保存已访问角色边，若同一边重复或移交次数超过阈值，就转管理者汇总或人工澄清。

### 步骤四：加入并行聚合与降级

课程匹配和简历检查可在输入就绪后并行执行，设置共同截止时间。超时角色返回缺席状态，聚合器基于已有证据生成部分结果并显式说明缺口。规则冲突交给确定性检查器，偏好冲突交给用户，不让模型自行抹平。

### 步骤五：完成对比与回归测试

在相同任务、相同模型和温度下比较基线与多智能体方案。除质量外，还测端到端 P95 延迟、总 Token、工具次数、移交次数和安全违规。若质量提升不足以抵消成本，应减少角色或回退单 Agent。

## 关键代码与配置

示例以程序侧状态约束移交次数与角色边界。生产实现还要持久化事件并验证每个角色的输出 Schema。

```python
from dataclasses import dataclass, field

@dataclass
class TeamRun:
    owner: str = "manager"
    handoffs: int = 0
    visited: set[tuple[str, str]] = field(default_factory=set)

def accept_handoff(state, payload, role_tools):
    source, target = state.owner, payload["target"]
    edge = (source, target)
    if target not in role_tools:
        return {"status": "rejected", "reason": "unknown_role"}
    if state.handoffs >= 4 or edge in state.visited:
        return {"status": "needs_human", "reason": "handoff_loop"}
    required = {"goal", "facts", "evidence", "expected_output"}
    if not required.issubset(payload):
        return {"status": "rejected", "reason": "incomplete_contract"}
    state.visited.add(edge)
    state.handoffs += 1
    state.owner = target
    return {"status": "accepted", "tools": sorted(role_tools[target])}
```

在配置中给每个角色独立设置最大调用次数和工具允许清单。团队总预算必须小于各角色预算简单相加，避免所有角色同时用满额度。路由决策包含 `reason_code`，便于按错误类型统计和优化。

## 调试和常见故障

### 故障一：两个角色不断相互移交

- 现象：课程顾问认为问题属于简历，简历教练又认为需要先选课程，事件时间线反复出现同一条边。
- 原因：角色卡的责任边界重叠，handoff 缺少期望产物；全局编排器没有记录访问边和移交上限。
- 定位：查看角色决策理由、移交载荷和 visited 集合，确认是否在没有新增事实时重复同一转移。
- 修复：规定接收者先产出最小结果再移交；补充 `expected_output`；检测重复边后交给管理者拆分任务或请用户确定优先级。

### 故障二：汇总答案遗漏关键风险

- 现象：安全审核员标记了简历包含个人证件号，最终答案却只呈现课程建议，没有风险警告。
- 原因：聚合器按固定顺序覆盖字段，或把超时与空结果混为一谈，没有为高优先级风险设置不可覆盖规则。
- 定位：比较各子输出、Schema 校验结果和合并后的字段溯源，检查风险事件是否到达聚合器。
- 修复：为安全告警使用独立集合并按严重级别合并；任何高风险结果必须进入最终响应或阻止提交；为缺席结果显式标记状态。

## 安全、成本与职业规范提示

最小权限必须落实到每个角色的真实工具注册，不依赖角色提示。简历等个人数据按任务需要裁剪，跨角色传递用摘要与引用，完成后按策略删除。安全角色的建议也可能错误，涉及拒绝服务、就业评价等高影响决策必须提供申诉和人工复核。

多智能体会成倍增加模型调用，必须设置团队 Token、时间和工具预算，并展示降级策略。能并行的任务不等于应该全部并行；先判断结果是否必要。职业工程师需要报告基线、改进和代价，不能只展示一次成功演示来证明复杂架构有效。

## 实训练习

1. 把一个不必要的角色改为普通函数，比较质量、延迟和可维护性。
2. 构造缺少证据的 handoff，验证接收角色拒绝并返回可修复原因。
3. 让两个角色对同一岗位匹配产生冲突，设计规则裁决与用户裁决两条路径。
4. 模拟安全审核员超时，检查最终页面是否明确显示“尚未完成安全检查”。
5. 编写工具越权测试，证明课程顾问无法读取简历原文或提交材料。
6. 用事件图找出最长调用链，提出一次减少 Token 和一次降低延迟的改造。

## 学习评价量表

| 评价维度 | 优秀 | 合格 | 需改进 |
|---|---|---|---|
| 拆分合理性 | 用基线证据证明角色必要 | 角色职责基本清楚 | 为复杂而拆分 |
| 移交契约 | 目标、事实、证据和预算完整 | 能结构化传递任务 | 用自然语言随意转交 |
| 冲突治理 | 可复现裁决并保留异议 | 有合并规则 | 后返回结果覆盖前者 |
| 运行控制 | 循环、超时和团队预算齐全 | 有次数和时间限制 | 角色可无限调用 |
| 安全与审计 | 角色级权限和链路证据完整 | 能记录角色调用 | 共享全部数据和工具 |

## 本项目小结

多智能体系统的价值来自清晰专业边界与可治理协作，而非角色数量。你通过基线定位问题，以角色卡限制能力，用 handoff 契约保持事实和证据，用全局状态阻止循环，并为冲突、超时和预算建立确定策略。只有当同集评测显示质量收益能够覆盖协调成本时，这套架构才应进入生产。
