# 项目四：编排复杂工作流

## 岗位情境

学习助理的“生成实训方案”任务包含读取课程要求、并行查询学生进度与可用资源、判断是否需要补充信息、生成草案、等待教师确认、再发布给学生。团队最初把所有条件写进一段提示词，让模型自由决定顺序。结果同一次请求可能先发布后确认，也可能在缺少学生目标时直接猜测，失败后无法从中间节点继续。

你需要把业务规则显式建模为状态化工作流。确定性步骤由程序控制，只有需要理解自然语言或生成内容的节点调用模型。工作流支持顺序、分支、并行、受控循环和人工确认，并在每个节点后保存检查点。目标不是追求复杂图形，而是让每条路径都有进入条件、输出契约、失败策略和恢复位置。

## 项目目标

- 能判断某个步骤应使用普通代码、模型决策还是人工确认。
- 能设计显式状态、节点输入输出和允许转移，避免隐式全局变量。
- 能实现顺序、条件分支、并行汇合和带上限循环。
- 能为副作用节点增加检查点、幂等键和人工审批。
- 能通过路径覆盖、故障注入和恢复测试验证工作流，而不依赖真实模型随机性。

完成后，学习者应能把一段含多个 if/then 的 Agent 提示转换为可检查工作流，并能说明并行是否安全、恢复是否会重复副作用。

## 项目产物与验收条件

- 输入：实训方案业务流程、节点依赖、风险分级、模拟学生资料和教师审批决定。
- 输出：状态模型、节点注册表、工作流执行器、检查点仓库和路径测试集。
- 验收证据：信息完整路径、补充信息路径、并行查询一项失败、教师拒绝、发布后恢复五组执行轨迹。
- 任意状态只能沿允许边迁移；循环有明确上限；并行节点不能写同一未协调字段。
- 恢复运行时已成功的副作用节点不得重复执行，最终报告能列出停留节点和原因。

## 任务分析

工作流设计先识别业务不变量，再画节点。课程 ID 必须始终存在、发布必须在审批之后，这些是程序约束；“学生目标是否清楚”可由规则和模型共同判断；“是否接受草案”属于人的决定。每个节点只做一件事，并返回结构化状态更新。节点之间通过状态契约通信，不直接调用彼此内部变量。

## 核心知识

### 显式状态机

工作流状态由稳定业务字段组成，例如运行 ID、课程 ID、目标、查询结果、草案版本、审批结果和已发布 ID。状态转移由当前节点结果和条件函数决定。把“下一步是什么”写进程序，使模型无法跳过必要校验。模型可以生成草案或提出路由建议，但最终边选择仍需符合允许转移表。

### 顺序、分支与循环

顺序适合严格依赖；分支用于互斥业务条件；循环只用于可测量的改进过程，例如草案最多修改两次。每次循环都要更新计数和失败原因。用“直到模型满意”为条件无法稳定测试，也可能无限消耗。分支条件尽量返回枚举而不是自由文本。

### 并行与汇合

只有没有写冲突、没有顺序依赖的节点才能并行。每个并行任务写入独立字段，汇合节点统一判断完整性。失败策略可以是全部成功、允许部分结果或快速失败，必须在设计时明确。并行不等于无限并发，还需设置总量、单节点超时和取消传播。

### 人工确认与检查点

人工节点把工作流状态设为 `waiting_for_human`，保存确认摘要、待审批版本和恢复令牌，然后结束当前执行。用户确认后从该节点继续，不重新生成草案。副作用节点执行前保存意图，执行后保存外部结果 ID；恢复时根据幂等键查询结果，避免重复发布。

## 工程实现步骤

### 步骤一：定义状态、节点结果和转移表

状态字段使用明确类型。节点返回 `updates`、`outcome` 和可选错误，不直接决定任意下一个函数。转移表把 `(node, outcome)` 映射到允许节点，未知 outcome 进入失败状态。建立图校验，启动前检查无目标节点和无上限循环。

### 步骤二：实现顺序与条件路由

先实现同步执行器，每次读取当前节点、调用 handler、合并允许字段并选择下一边。请求不完整时进入 `ask_clarification` 并暂停；收到补充后回到校验节点。对每个分支编写固定输入测试。

### 步骤三：增加并行加载和汇合

把进度与资源查询放入受限线程池或异步任务组，分别记录结果和错误。汇合策略允许资源服务失败时使用默认资源，但进度查询失败则停止生成。任何一个任务取消时传播取消信号并等待清理。

### 步骤四：增加人工审批、检查点和恢复

教师审批前保存完整草案和摘要。审批拒绝可进入一次修改循环，超过次数转人工编辑。发布使用运行 ID 与草案版本生成幂等键。模拟进程在发布响应前退出，验证恢复逻辑不会创建第二份方案。

## 关键代码与配置

```python
TRANSITIONS = {
    ("validate", "ready"): "load_context",
    ("validate", "missing"): "ask_human",
    ("load_context", "ok"): "draft",
    ("draft", "ok"): "review",
    ("review", "approved"): "publish",
    ("review", "revise"): "draft",
    ("publish", "ok"): "finish",
}

def advance(state, nodes):
    node = state["node"]
    result = nodes[node](state.copy())
    state.update(result.get("updates", {}))
    edge = (node, result["outcome"])
    if edge not in TRANSITIONS:
        return {**state, "status": "failed", "reason": "invalid_transition"}
    return {**state, "node": TRANSITIONS[edge]}
```

示例省略了循环计数、字段白名单、并行和持久化，重点是节点只能沿显式边前进。生产实现应在每次 `advance` 后原子保存检查点。

## 调试和常见故障

### 故障一：并行节点互相覆盖状态

- 现象：资源查询完成后，先完成的学生进度结果偶尔消失，问题只在并发运行时出现。
- 原因：两个任务都复制并回写完整状态，后完成者用旧快照覆盖另一任务字段。
- 定位：查看节点更新集合和时间线，确认 handler 是否返回整个 state 而非自己的字段增量。
- 修复：每个并行节点只写独占命名空间；汇合节点在单线程合并，检测同字段冲突并拒绝运行。

### 故障二：恢复后重复发布训练方案

- 现象：服务在发布响应前重启，恢复运行后学生收到两份相同方案。
- 原因：检查点只记录“准备发布”，没有幂等键和外部结果查询，执行器把未知结果当成未执行。
- 定位：关联发布请求、运行 ID 和草案版本，检查外部系统是否已经存在相同幂等键记录。
- 修复：发布前持久化幂等键，外部接口按键去重；恢复时先查询，再决定补写结果或执行。

## 安全、成本与职业规范提示

确定性规则不应交给模型重复判断，这既降低成本也减少绕过风险。模型节点只接收完成任务所需字段，工具结果和外部文本仍视为不可信。审批界面要显示草案版本、目标对象和将要发生的副作用，不能只提供含糊的“继续”按钮。

并行会提高瞬时调用量，需要总并发和预算。检查点不得保存明文密钥；恢复令牌应不可猜测且绑定用户。任何失败都要保留当前节点和安全消息，不能把技术失败包装成业务完成。流程变更应提升版本，旧运行按原版本恢复或明确迁移。

|---|---|---|---|
| 状态建模 | 字段、节点契约和边完整 | 有显式状态与分支 | 依赖提示隐式推进 |

## 本项目小结

工作流把复杂任务从一段不可观察的提示转换为显式状态、节点和边。程序守住业务不变量，模型处理真正需要语义判断的部分，人工控制高风险决定。并行必须有独立输出与汇合策略，循环必须有上限，副作用必须有检查点和幂等。这样的编排才能在失败后解释、恢复和继续。
