# 项目二：开发可靠工具系统

## 岗位情境

学习助理 Agent 需要读取课程目录、查询学生进度并创建训练草稿。开发团队直接把三个 Python 函数交给模型，其中一个函数同时支持查询、修改和删除。测试时模型偶尔把课程名称放进学生 ID 字段；网络超时后又重复创建两份草稿。安全评审指出，工具描述写得再清楚，也不能替代程序侧权限和参数校验。

你需要建设一个可靠工具层：模型看到的是窄而明确的工具契约，执行器看到的是经过校验和授权的调用请求，业务系统看到的是带幂等键、超时和审计信息的受控操作。最终系统必须区分“模型提出工具调用”“执行器接受调用”和“外部系统确认成功”三个事实。

## 项目目标

- 能按照数据工具、行动工具和编排工具分析权限与副作用。
- 能为工具定义稳定名称、用途说明、输入 Schema、输出类型和错误分类。
- 能在执行前完成白名单、身份、资源范围和参数校验。
- 能为写操作设计幂等键、超时、有限重试、人工确认与审计事件。
- 能用工具替身测试成功、参数错误、超时、重复请求和未授权请求。

完成后，学习者应能解释工具 Schema 为什么既服务模型选择，也服务程序验证，并能拒绝“万能 HTTP 请求”“任意 SQL”“执行任意命令”等开放式高风险工具。

## 项目产物与验收条件

- 输入：三个业务能力说明、调用者身份、允许资源范围以及风险分级表。
- 输出：`ToolSpec`、注册表、受控分发器、统一结果对象和工具审计日志。
- 验收证据：合法读取、非法字段、越权资源、写操作确认、超时重试和幂等去重六组测试。
- 每个工具只暴露完成岗位任务所需的最小功能；读取与修改不得藏在同一模糊工具中。
- 所有失败返回稳定错误代码，模型可据此修正，但错误响应不得泄露密钥和内部堆栈。

## 任务分析

工具层位于模型和真实系统之间。模型输出不可信，外部响应也可能不可信，因此工具层需要双向验证：向下验证模型参数和权限，向上规范外部结果。可靠性来自契约和执行控制，不来自更长的工具描述。每个工具还需要说明是否只读、是否可重试、是否幂等、是否需要用户确认。

### 风险分级

只读查询通常为低风险，但仍需资源范围和隐私过滤；创建草稿可逆，属于中风险，可由策略自动允许；发送、支付、删除等真实副作用属于高风险，必须显示参数并获得人工确认。风险不是由工具名称决定，而由功能、权限、可恢复性和影响对象共同决定。

## 核心知识

### 工具契约的五个部分

第一是唯一且稳定的名称，避免多个工具含义重叠；第二是面向决策的说明，写清何时使用和何时不用；第三是输入 Schema，限定类型、枚举、长度和必填字段；第四是输出契约，区分数据、业务失败和系统失败；第五是执行策略，包括权限、超时、幂等、重试与确认。

Schema 不是提示词装饰。即使模型供应商声称支持严格结构化输出，应用仍必须在本地重新校验。字段描述要说明业务单位和范围，例如 `mastery` 是 0 到 1 的小数，而不是含糊的“掌握度”。输出也应收窄，只返回任务需要的数据，不把数据库整行或内部错误直接放回模型上下文。

### 白名单与最小权限

注册表是模型可调用工具的唯一来源。模型返回未知名称时，执行器应拒绝并记录，而不是通过反射寻找同名函数。工具内部使用专用低权限凭据，并根据当前用户进一步限制资源。课程助理查询进度时只应读取本人的课程记录，不能依赖模型在参数里“自觉”填写正确用户。

### 幂等与重试

读取工具通常可以对连接超时有限重试；写工具只有在具备幂等键或确认外部系统未执行时才能重试。幂等键由应用基于运行 ID、步骤和规范化业务参数生成，不能由模型随意提供。超时表示“结果未知”，不一定表示“操作未发生”，因此写操作超时后应先查询状态，再决定是否重试。

### 错误是协议的一部分

统一工具结果可包含 `ok`、`code`、`data`、`retryable` 和用户安全消息。参数错误返回可修正字段；权限错误不可重试并转人工；限流错误携带最早重试时间；外部系统异常记录关联 ID。模型只看到必要摘要，完整堆栈留在受保护日志中。

## 工程实现步骤

### 步骤一：拆分业务能力并登记风险

把“管理学习记录”拆为 `get_progress`、`create_training_draft` 等窄工具。为每个工具记录只读性、风险级别、允许角色、资源解析器、超时和幂等策略。删除当前任务不需要的修改与删除能力。

### 步骤二：实现 Schema 校验与上下文授权

调用请求包含工具名、原始参数、运行 ID 和当前身份。先从注册表取规范，再使用数据模型校验参数。身份和学生 ID 的绑定由服务端上下文完成，不接受模型覆盖。高风险调用在执行前生成确认摘要并暂停运行。

### 步骤三：实现受控分发与结果归一化

分发器只调用注册表中的显式 handler，设置超时并把业务异常映射为稳定错误。输出经过字段选择和长度限制后再回写 Agent 状态。敏感值在日志和模型上下文中分别脱敏。

### 步骤四：加入幂等、测试替身与审计

写操作根据运行信息生成幂等键，保存请求指纹和结果引用。测试中用内存工具替身模拟首次超时但实际成功的场景，验证程序先查状态而不是盲目重复写入。审计事件记录调用者、工具、资源、策略决定和结果代码。

## 关键代码与配置

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class ToolSpec:
    name: str
    handler: object
    allowed_roles: frozenset[str]
    requires_confirmation: bool = False

class ToolDispatcher:
    def __init__(self, specs):
        self.specs = {item.name: item for item in specs}

    def call(self, name, arguments, context):
        spec = self.specs.get(name)
        if not spec:
            return {"ok": False, "code": "unknown_tool"}
        if context.role not in spec.allowed_roles:
            return {"ok": False, "code": "forbidden"}
        clean = context.validators[name](arguments)
        if spec.requires_confirmation and not context.confirmed:
            return {"ok": False, "code": "confirmation_required"}
        return {"ok": True, "data": spec.handler(context=context, **clean)}
```

生产实现还需用独立线程或异步超时包裹 handler，并限制输出大小。不要把 `globals()`、任意模块导入或 shell 执行暴露给模型。

## 调试和常见故障

### 故障一：超时后生成重复草稿

- 现象：一次 Agent 步骤对应两个内容相同、ID 不同的训练草稿。
- 原因：第一次请求在服务端成功但响应丢失，执行器把超时误判为未执行并直接重试。
- 定位：用运行 ID 和请求指纹查询审计日志，比较两次写请求是否缺少相同幂等键。
- 修复：应用生成幂等键；超时后先按键查询结果，只有确认未执行时才进行有限重试。

### 故障二：模型通过参数读取其他学生数据

- 现象：工具参数中的学生 ID 与当前登录身份不一致，但查询仍返回数据。
- 原因：工具把模型提供的资源标识当成授权依据，没有在服务端做对象级权限校验。
- 定位：检查 handler 是否从可信上下文获取用户，审计日志是否同时记录调用者和目标资源。
- 修复：从认证上下文绑定学生 ID；对管理员等例外角色使用显式策略，拒绝模型覆盖受保护字段。

## 安全、成本与职业规范提示

工具说明、第三方 MCP 注解和模型参数都属于不可信输入。最小化工具数量和权限，避免开放式 URL、SQL、文件路径与命令执行。写操作要明确可恢复性，高风险操作必须让用户看见对象和影响后再确认。工具返回的网页或文档可能包含提示注入，不能因为内容来自“工具”就提升可信级别。

超时、重试和输出长度直接影响成本。为每个工具设置调用次数、并发和结果大小限制；对频繁读取使用带权限键的短期缓存。日志应记录策略决定和关联 ID，但隐藏凭据、个人敏感数据及不必要的原始内容。

## 实训练习

1. 为 `create_training_draft` 设计输入 Schema，限制标题长度、课程 ID 格式和内容大小。
2. 实现“首次请求超时但服务端已成功”的工具替身，验证幂等去重。
3. 把一个万能管理工具拆成至少三个窄工具，并写出各自不用的场景。
4. 为低、中、高风险工具设计不同确认策略和审计字段。
5. 对工具输出加入敏感字段过滤与最大字符数，测试嵌套对象和超长列表。

## 本项目小结

工具系统是 Agent 与真实世界之间的安全边界。模型只能提出符合契约的调用，应用负责验证、授权、确认、执行和审计。窄工具比万能工具更容易选择、测试和授权；稳定错误比堆栈更有利于恢复；幂等和状态查询共同避免重复副作用。下一项目将在不扩大工具权限的前提下，把运行状态扩展为可控记忆。
