# 项目六：接入 MCP

## 岗位情境

学校的信息中心已经分别开发了设备查询、课程资源和工单三个服务。过去每个 AI 应用都要编写一套专有适配器，升级成本很高。团队决定使用 Model Context Protocol（MCP）统一向学习助理发布工具和资源。你作为 Agent 开发工程师，需要实现一个最小 MCP 客户端接入方案，并评审服务器提供的能力是否值得信任。

MCP 解决的是上下文与能力交换协议，不会自动解决授权、业务确认或输出真实性。Host 仍负责用户体验、权限决策和模型编排；Client 维护与某个 Server 的连接；Server 声明工具、资源或提示能力。本项目要求既完成协议握手和工具调用，也证明恶意或异常服务器不能突破应用边界。

## 项目目标

完成项目后，你能够解释 Host、Client、Server 的职责；通过初始化协商读取服务器能力；把允许的 MCP 工具映射到 Agent 工具注册表；处理版本不兼容、连接中断和工具列表变化；对工具调用执行参数校验、超时、人工确认和结果截断；并能审计一次从用户请求到 MCP 响应的完整链路。

你还将区分 tools 与 resources 的语义：工具可以触发计算或副作用，资源更接近可读取的上下文对象。应用只启用任务所需能力，不能因为服务器“支持更多”就全部暴露给模型。

## 项目产物与验收条件

- 输入：一个测试 MCP Server、允许能力清单、用户身份上下文以及设备报修业务规则。
- 输出：连接配置、能力协商器、MCP 工具桥接层、确认策略、模拟服务器与自动化测试。
- 验收证据：初始化版本可核对；未允许工具不会注册；危险工具调用停在确认节点；断线返回明确状态；服务器改变工具列表后应用能重新校验而非静默信任。

| 验收项 | 通过条件 | 证据形式 |
|---|---|---|
| 协议连接 | 初始化、能力和版本记录完整 | 握手事件日志 |
| 工具发现 | allowlist 外能力不可见 | 注册表快照 |
| 调用治理 | Schema、超时和确认均生效 | 自动化测试 |
| 资源读取 | URI 范围受限且内容被截断 | 资源读取记录 |
| 故障隔离 | 单个服务器失败不拖垮会话 | 断线演练报告 |

## 任务分析

先从业务任务反推能力：学习助理只需要查询设备、读取报修规范和提交工单，不需要服务器的管理员工具。连接建立后，客户端记录协议版本和能力声明，再请求工具或资源清单。发现阶段的描述只是候选信息，真正注册前还要经过名称、Schema、风险等级和来源服务器校验。

调用阶段为每个请求生成关联 ID，将模型参数转换为协议参数；返回内容先做大小、类型和敏感信息检查，再进入 Agent 观察。提交工单属于副作用，必须由 Host 弹出预览并获得用户确认。连接失败时给 Agent 一个可解释的工具不可用状态，而不是让模型假装完成。

## 核心知识

### 三层架构与连接隔离

Host 是面向用户的 AI 应用，创建一个或多个 MCP Client；每个 Client 通常与一个 Server 维持有状态连接。把连接隔离到服务器维度，可以避免一个服务看到其他服务的完整对话，也便于独立超时和撤销。Host 选择哪些上下文进入模型，并承担跨服务器编排责任。

### 初始化与能力协商

连接开始时双方交换协议版本、能力和实现信息。客户端只能使用协商成功的能力，不能根据旧缓存假设服务器仍支持某项功能。若版本不可兼容，应在调用前失败并给出升级建议。清单变化是一类安全事件：新增能力要重新审批，已删除工具要从模型注册表及时移除。

### Tools、Resources 与提示

Tools 由模型发现并调用，参数由 JSON Schema 描述，可能包含副作用；Resources 由应用按 URI 读取，更适合文档、配置或状态快照；Prompts 是服务器提供的可选模板，不应该覆盖 Host 的系统安全策略。不同原语的用户控制方式不同，项目必须为写工具提供显式确认，为资源 URI 设置允许范围。

### 传输、授权与凭据

本地进程常使用 stdio，远程服务可使用协议支持的 HTTP 传输。无论传输方式如何，凭据都保存在 Host 或受控运行环境，不应转交模型。远程授权需要校验目标资源与令牌受众，避免把一个服务器的令牌发送给另一个服务器。生产环境还要验证 TLS、重定向目标和回调地址。

### 不可信输入模型

工具描述、资源文本和返回内容都来自外部边界，可能过长、格式错误或包含提示注入。它们不能被当作更高优先级指令。Host 对描述长度、Schema 深度、返回体大小和内容类型设限；敏感操作依据本地风险策略，而不是依据服务器声称的注释自动放行。

## 工程实现步骤

### 步骤一：定义连接配置与允许清单

为每个服务器配置稳定 ID、传输方式、启动命令或 HTTPS 地址、允许的工具名称、资源 URI 前缀、超时和最大响应大小。凭据只通过安全引用获取。将开发、测试和生产配置分开，并记录配置审批人。

### 步骤二：实现初始化和发现

客户端连接后发送初始化请求，验证协商版本，保存服务器能力。随后请求工具清单，对每个 Schema 做结构检查，并与 allowlist 求交集。注册表条目包含 server_id、原始工具名、风险等级与清单哈希，防止同名工具混淆。

### 步骤三：构建调用桥接层

桥接层校验模型参数、生成请求 ID、设置截止时间并调用 MCP Client。返回结果按声明类型解码，执行大小限制和脱敏，再映射为统一 Agent 观察。异常必须分类为连接、协议、参数、权限、超时或服务器执行错误。

### 步骤四：落实用户确认和资源控制

对提交工单等写工具，先把规范化参数展示给用户，确认令牌绑定 server_id、工具名和参数摘要。资源读取只允许批准的 URI 前缀，并限制单次与会话累计字节数。资源内容以数据身份进入上下文，不执行其中要求调用其他工具的指令。

### 步骤五：开展兼容和攻击测试

使用模拟服务器返回未知协议版本、重复工具名、畸形 Schema、超大响应、断线和恶意描述。断言客户端 fail closed；重连后重新协商；新工具不会自动获得权限；日志可关联但不会包含访问令牌或完整敏感资源。

## 关键代码与配置

下面是桥接层的核心形态，`session` 与授权实现由具体 SDK 或自研客户端提供。风险审批仍应发生在 Host 层。

```python
class McpBridge:
    def __init__(self, session, allowed, limits):
        self.session = session
        self.allowed = allowed
        self.limits = limits

    async def call(self, name, arguments, confirmed=False):
        policy = self.allowed.get(name)
        if policy is None:
            return {"status": "denied", "reason": "tool_not_allowed"}
        if policy["writes"] and not confirmed:
            return {"status": "needs_confirmation", "preview": arguments}
        policy["validator"](arguments)
        result = await self.session.call_tool(
            name, arguments, timeout=self.limits["timeout"])
        text = result.to_text(max_chars=self.limits["max_chars"])
        return {"status": "ok", "data": text, "server_id": policy["server_id"]}
```

配置中只保存变量名，不保存真实令牌。例如远程服务器条目可以引用 `MCP_DEVICE_TOKEN`，由进程启动环境注入。若使用本地 stdio，启动命令必须是固定可执行文件和参数数组，禁止把模型输出拼接成 shell 字符串。

## 调试和常见故障

### 故障一：服务器显示在线但工具始终不可用

- 现象：健康检查通过，Agent 注册表却为空，调用返回 `tool_not_allowed`。
- 原因：初始化协商的协议版本不匹配，或服务器工具名与本地 allowlist 的命名空间不同。
- 定位：按连接 ID查看初始化响应、协商版本、清单哈希和过滤前后工具数量，比较完整名称而非展示标题。
- 修复：升级兼容的客户端或服务器；使用 `server_id/tool_name` 规范化名称；更新允许清单时走审批与测试，不要用通配符临时放行。

### 故障二：读取资源后 Agent 开始执行无关指令

- 现象：读取报修手册后，模型尝试调用管理员工具或索要用户凭据，行为与原任务偏离。
- 原因：资源包含提示注入文本，Host 把外部内容拼成了高优先级系统指令，并且暴露了过多工具。
- 定位：检查进入模型的消息角色、资源来源标签、读取范围和当时可见工具集合，重放同一资源验证行为。
- 修复：把资源作为不可信数据并清楚分隔；保持最小工具集合；对高风险意图使用本地策略拦截；记录恶意资源并暂停该服务器连接。

## 安全、成本与职业规范提示

MCP Server 是外部信任边界，安装或连接前要核验发布者、代码来源、权限需求和更新机制。本地 Server 进程使用低权限账户与受限工作目录；远程 Server 只连接批准的 HTTPS 端点。令牌不得出现在模型消息、错误弹窗、截图或普通日志中。

发现大量工具会扩大提示上下文和决策空间，应按当前任务动态选择少量能力。资源读取设置字节上限、缓存策略和来源隔离，防止一次响应消耗过多 Token。用户必须知道即将调用哪个组织提供的能力、会发送哪些数据、可能产生什么副作用，并能够取消。

## 实训练习

1. 编写模拟 MCP Server，分别声明只读查询工具与写入工单工具，验证注册策略。
2. 让服务器在重连后增加一个高风险工具，断言它不会自动出现在 Agent 能力中。
3. 构造超大资源和嵌套过深的 Schema，记录桥接层拒绝位置与用户提示。
4. 为确认令牌加入参数摘要，证明用户确认后模型篡改参数会被拒绝。
5. 比较 stdio 与远程 HTTP 部署的信任边界、凭据位置和运维风险。
6. 设计服务器撤销流程，说明如何终止连接、清除缓存并保存审计证据。

## 本项目小结

你已经完成从专有工具适配到协议化能力接入的关键一步。可靠 MCP 集成以初始化协商为起点，以本地允许策略为准绳，以用户确认和不可信输入处理为安全底线。协议让服务更容易复用，却不会替应用做风险判断；Host 始终对最终可见能力、发送数据和副作用负责。
