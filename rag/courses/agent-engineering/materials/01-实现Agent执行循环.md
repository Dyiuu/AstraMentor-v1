# 项目一：实现 Agent 执行循环

## 岗位情境

某职业院校准备把“课程咨询机器人”升级为能够完成连续任务的学习助理。旧程序只能把一句问题交给模型并显示答案，遇到“先查课程要求，再比较学生进度，最后给出下一步训练任务”时，会把尚未查询的数据当成事实，或者连续调用同一个接口而无法结束。你作为 Agent 开发工程师，需要实现一个不依赖特定框架的最小执行循环，让模型只能在明确状态中选择行动，并让程序而不是模型掌握次数、超时和终止权。

岗位要求并不是让模型“尽可能自主”，而是把不确定决策约束在可观察、可测试的循环中。最终系统需要回答三个工程问题：当前做到哪一步、为什么继续或停止、发生异常后留下了什么证据。该循环将成为后续工具、记忆和工作流项目的共同运行内核。

## 项目目标

- 能区分普通模型调用、确定性工作流与 Agent 执行循环的适用边界。
- 能设计包含目标、观察、行动、步骤号和状态的运行上下文。
- 能实现“模型决策—参数校验—行动执行—观察回写—终止判断”的闭环。
- 能同时设置业务完成条件、最大步数、截止时间、人工中止和错误阈值。
- 能通过事件日志复盘一次运行，而不是只查看最终自然语言答案。

完成后，学习者应能解释为什么“模型没有继续调用工具”不等于任务成功，也能说明为什么最大步数只是安全兜底而不是业务完成条件。

## 项目产物与验收条件

- 输入：用户目标、允许行动列表、初始上下文、最大步骤数和运行截止时间。
- 输出：一个可运行的 `AgentRunner`、结构化运行事件、明确的最终状态与面向用户的结果。
- 验收证据：正常完成、达到步数上限、人工取消、工具失败四组测试记录；每组都包含运行 ID、步骤事件和终止原因。
- 代码不得让模型直接修改循环计数、截止时间或允许工具集合。
- 相同的模拟决策序列应产生相同的状态迁移，便于编写回归测试。

## 任务分析

执行循环由控制面和决策面组成。模型属于决策面，只负责在当前观察下提出下一行动；程序属于控制面，负责验证行动、执行工具、更新状态并决定是否结束。两者混在一个大函数中，会造成错误无法归因：既不知道模型选错了，还是参数校验漏了，也不知道工具成功后状态有没有写回。

### 任务边界

本项目只实现单 Agent 顺序循环，不接入长期记忆、多智能体和 MCP。行动执行器使用本地无副作用函数，避免把外部系统权限问题与循环设计混为一谈。真实模型可以在接口稳定后替换模拟决策器，但测试必须继续使用确定性替身。

## 核心知识

### Agent 与聊天调用的差别

聊天调用的程序路径通常是“输入—模型—输出”，模型没有通过工具改变外部状态，也不控制后续步骤。Agent 则由模型在循环中选择行动，程序把行动结果作为新观察再次交给模型，直到满足退出条件。判断一个系统是不是 Agent，重点不在名称，而在模型是否参与工作流执行决策、是否能基于观察调整下一步。

### 状态与事件分离

状态表示当前事实，例如 `step=2`、已取得课程目录、待确认训练计划；事件表示事实如何变化，例如模型选择 `lookup_progress`、工具返回超时、用户点击取消。状态用于下一次决策，事件用于追踪和审计。只保存最终状态会丢失过程，只保存日志又难以恢复运行，因此两者都需要。

建议状态至少包含运行 ID、用户目标、当前步骤、观察列表、连续错误数、开始时间和取消标记。事件至少包含时间、步骤、类型、行动名称、参数摘要、结果摘要和错误类别。敏感参数只记录掩码或摘要。

### 多层终止条件

业务完成条件回答“任务是否真的交付”，例如已经生成训练建议且引用了学生进度。模型返回普通文本只能作为完成候选，程序仍需校验输出结构。安全条件包括最大步骤、截止时间、连续失败阈值和人工取消。任何一个安全条件触发都应返回明确的未完成状态，不能伪装为成功答案。

### 可恢复错误与不可恢复错误

参数缺少字段、临时超时可以反馈给模型一次，让它修正或重试；工具未授权、用户取消、超过预算属于不可恢复条件，应立即结束。没有错误分类的“自动重试”容易放大成本并产生重复副作用。重试次数属于控制面，模型不能自行决定无限重试。

## 工程实现步骤

### 步骤一：定义运行状态与决策契约

使用数据类描述 `RunState` 和 `Decision`。决策类型只允许 `tool`、`finish`、`ask_human`，工具名必须来自白名单。模型输出先解析为决策对象，解析失败记录为一次可恢复错误，不能把原始文本直接交给执行器。

### 步骤二：实现单步执行函数

单步函数依次检查取消、截止时间和步数，调用决策器，验证决策，再执行无副作用工具。工具结果以观察对象写回状态。单步函数只前进一步，使单元测试能够逐步断言状态，不必启动完整循环。

### 步骤三：实现循环与终止报告

循环重复调用单步函数，直到得到完成、需要人工处理或安全停止。最终报告包含 `status`、`reason`、`output` 和事件列表。为每次运行生成不可猜测的运行 ID，但测试可注入固定 ID 和时钟。

### 步骤四：用决策替身覆盖边界

准备四组固定决策：一次完成、连续工具调用后完成、永远调用同一工具、先给非法参数再修正。通过替身验证循环，而不是依赖真实模型的随机输出。再加入取消事件和可控时钟，验证取消与截止时间优先于下一次模型请求。

## 关键代码与配置

```python
from dataclasses import dataclass, field

@dataclass
class RunState:
    goal: str
    step: int = 0
    observations: list[str] = field(default_factory=list)
    cancelled: bool = False

def run_agent(state, decide, tools, max_steps=6):
    while state.step < max_steps and not state.cancelled:
        action = decide(state)
        if action["type"] == "finish":
            return {"status": "completed", "output": action["output"]}
        name = action.get("tool")
        if name not in tools:
            state.step += 1
            continue
        observation = tools[name](**action.get("arguments", {}))
        state.observations.append(str(observation))
        state.step += 1
    reason = "cancelled" if state.cancelled else "max_steps"
    return {"status": "incomplete", "reason": reason}
```

生产代码还需加入单调时钟、参数 Schema、超时、运行 ID 和结构化日志。本段代码用于说明控制权必须在程序侧，不应直接复制为开放外部权限的执行器。

## 调试和常见故障

### 故障一：循环重复调用同一工具

- 现象：事件日志显示相同工具和近似参数连续出现，Token 与调用次数持续增加。
- 原因：工具结果没有写回观察，或提示中缺少已经完成的事实，模型认为行动尚未执行。
- 定位：比较相邻步骤的状态快照，检查 observations 是否新增，并核对工具结果是否被错误截断。
- 修复：把结构化结果写入状态；增加“相同行动指纹连续两次”检测，触发纠错提示，第三次则安全停止并交给人工。

### 故障二：模型说完成但产物不存在

- 现象：最终文本声称训练计划已保存，但存储中没有对应记录。
- 原因：程序把自然语言 `finish` 直接当成业务成功，没有校验必需产物和证据。
- 定位：查看 finish 事件与外部产物 ID，确认完成决策是否携带可验证字段。
- 修复：为完成输出定义 Schema；终止前执行确定性验收函数，缺少产物时把失败原因作为观察回写或转人工。

## 安全、成本与职业规范提示

循环越长，成本和副作用风险越高。所有运行必须设置最大步数、截止时间和预算；写操作工具默认需要用户确认。日志要足以审计，但不能记录访问令牌、完整个人信息或工具原始敏感响应。对用户展示“未完成”和真实原因，比用流畅文字掩盖失败更符合工程职业规范。

Agent 不应拥有比业务任务更多的工具。高风险工具采用最小权限账户，执行前显示行动对象、影响范围和可恢复性。人工取消信号应在每次模型调用和工具调用之前检查，取消后不得继续启动新副作用。

## 实训练习

1. 增加 `deadline` 和可注入单调时钟，编写恰好在截止时间触发的边界测试。
2. 为行动计算“工具名+规范化参数”指纹，实现重复调用保护并说明阈值选择。
3. 设计 `completed/incomplete/needs_human/failed` 四种最终状态，给出每种状态的用户提示。
4. 使用固定决策序列重放一次历史运行，验证状态迁移与原事件一致。
5. 分析一个不适合 Agent 的确定性业务流程，并说明改用普通代码的原因。

## 本项目小结

可靠 Agent 的第一能力不是“聪明”，而是可终止、可观察、可复现。模型提出下一步，程序验证和执行；业务条件证明完成，安全条件限制损失；状态支持继续工作，事件支持解释历史。掌握这一控制边界后，后续增加工具、记忆和多智能体时才不会把复杂度变成无法定位的自动化风险。
