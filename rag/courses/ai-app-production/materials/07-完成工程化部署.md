# 项目七：完成 AI 应用容器化部署与回滚

## 岗位情境

团队准备把职业学习 Agent 从开发电脑交付到学校测试环境。当前启动依赖手工激活虚拟环境、复制配置和执行索引命令；同一份代码在不同机器使用了不同 Python 包。运维曾把模型密钥写入镜像层，删除容器后仍能从历史层读取。一次新版本启动时课程索引尚未完成，健康检查只确认端口开放，流量立即进入并产生大量 409；另一次升级失败后没有旧镜像和数据备份，只能现场修代码。

你作为 AI 应用运维工程师，要把服务封装为可复现、可检查、可配置、可回滚的交付单元。任务覆盖镜像构建、非 root 运行、配置与密钥注入、存储边界、存活与就绪检查、优雅停机、持续集成门禁、镜像签名或摘要记录、分阶段发布和回滚演练。部署不是把 `docker run` 跑起来，而是证明新环境能按同一流程恢复服务并保留课程与会话数据。

AI 服务还依赖模型供应商和本地 RAG。存活表示进程能够工作，就绪表示当前实例可以接收业务流量；外部模型短时不可用不一定要杀死进程，课程索引未 ready 却不能承接课程请求。健康语义必须反映这些差异。

## 项目目标

完成本项目后，你应能编写最小化、可复现的容器镜像，区分构建时与运行时配置，使用外部秘密管理而非把凭据写入镜像。你应能设计 liveness、readiness 和 startup 检查，规划持久卷、备份与恢复，建立包含测试、安全扫描和制品记录的 CI/CD，并执行滚动发布、冒烟验证和一键回滚。

达成标准是：在一台干净主机上仅凭版本化部署文件即可启动；镜像中没有真实密钥；未就绪实例不接收流量；终止时能停止新请求并处理在途流；候选版本故障后能够恢复旧镜像和兼容数据，且回滚步骤经过实际演练。

## 项目产物与验收条件

输入包括应用源代码、依赖锁定文件、运行配置清单、数据目录、健康语义、质量门禁和目标运行环境。输出包括 Dockerfile、忽略文件、部署配置、健康接口、CI/CD 流程、制品清单、发布运行手册、备份恢复与回滚记录。验收证据包含镜像摘要、扫描报告、干净环境启动日志、探针状态和一次故障回滚时间线。

- 相同提交能够重复构建，运行时版本与依赖可追踪。
- 镜像使用非 root 用户，构建上下文不包含密钥、会话和本地索引临时文件。
- 配置在启动时注入并校验，缺少必需项时快速失败且不回显值。
- startup、liveness、readiness 含义分离，索引未 ready 时不接收课程流量。
- 持久数据目录明确挂载、备份、恢复和版本兼容策略。
- 发布前自动执行测试、镜像扫描和冒烟，失败阻断部署。
- 能在约定恢复时间内回滚到上一制品，并验证核心课程路径。

部署产物中的所有镜像、配置和脚本都要有版本。只保存 `latest` 标签、没有摘要和变更记录，不能通过验收。

## 任务分析

先盘点进程、端口、外部依赖和数据，再定义镜像与运行环境边界；随后实现健康接口与优雅停机，建立持续集成构建和门禁；最后在测试环境执行首次部署、候选升级和故障回滚。每一步都以“另一名运维能否重复”为检查标准，手工命令要进入运行手册或自动化配置。

### 环境分层

开发、测试和生产使用同一镜像，只通过运行时配置改变允许来源、模型别名、数据目录和观测出口。禁止为不同环境手工改源码。模型供应商能力和课程索引属于运行依赖，启动检查要报告状态，但不能在每个副本中不受控地并发重建同一索引。

## 核心知识

### 镜像、配置与制品可信度

镜像应固定基础运行时与依赖版本，采用多阶段构建减少编译工具和缓存进入最终层。`.dockerignore` 排除版本库、虚拟环境、用户数据、测试临时文件和本地配置。容器以专用非 root 用户运行，文件只给予必要权限，根文件系统尽量只读，可写内容定向到持久卷或临时目录。

构建参数会留在历史或制品元数据，不适合传递密钥。密钥在运行时由平台秘密机制挂载或注入，应用只读取必要名称；错误日志只能提示哪个配置缺失，不能打印其值。每个镜像记录源码提交、构建时间、依赖清单和不可变摘要，发布引用摘要而非可被覆盖的标签。

### 健康检查与生命周期

Startup probe 判断应用是否完成慢启动，例如配置解析、必要目录可写和基础课程注册；通过前不执行 liveness。Liveness 判断进程内部是否陷入不可恢复状态，失败会触发重启；它不应依赖容易短时波动的外部模型。Readiness 判断是否可以接收新流量，可检查关键本地索引、连接池和停止标志；失败时实例继续运行但从负载均衡移除。

优雅停机收到终止信号后先变为 not ready，停止接收新请求，等待在途流式响应和状态写入到限时，然后关闭连接与遥测。超时后仍要安全退出。若工具可能产生副作用，执行状态需幂等化，重启后能够判断已完成、待确认或可重试。

### 持续交付、数据与回滚

流水线依次执行静态检查、单元与组件测试、课程结构校验、镜像构建、依赖与镜像扫描、制品签名或摘要登记、测试环境部署、健康与冒烟。生产发布采用滚动或金丝雀，先让少量流量验证错误率、延迟和质量信号，再扩大。门禁失败自动停止，不边发布边临时修改镜像。

回滚不仅是换镜像。若新版本改变会话格式、索引 schema 或配置，旧版本可能无法读取新数据。变更前要设计向后兼容、双读或迁移备份，明确恢复点目标与恢复时间目标。索引可由 Markdown 重建，但用户会话和人工确认记录不可随意丢弃。回滚演练必须同时验证版本、数据和关键路径。

## 工程实现步骤

### 步骤一：整理运行契约并构建镜像

列出必需与可选配置、端口、数据目录、临时目录和外部依赖。锁定 Python 依赖，编写多阶段 Dockerfile，创建非 root 用户，复制必要文件并设置只读权限。使用干净构建检查上下文，导出软件物料清单或依赖列表，记录镜像摘要。

### 步骤二：实现探针和优雅停机

新增轻量健康接口：存活不调用真实模型，就绪读取实例停止状态和必要本地资源。启动阶段给索引扫描合理时间，构建任务由单独流程负责。捕获终止信号，先关闭 readiness，再等待在途请求；用一个长流式请求验证停机不会立即截断或重复提交状态。

### 步骤三：建立流水线与环境配置

将测试、内容校验、编译、镜像扫描和冒烟写入流水线。按环境维护非敏感配置，密钥由部署平台引用。流水线输出应用版本、镜像摘要、测试报告和变更说明。只有通过批准的制品可以进入下一环境，不能在服务器上直接构建未知代码。

### 步骤四：执行发布与回滚演练

先部署旧版并制造一条可恢复学习会话，再发布候选版。注入 readiness 失败或错误率升高，验证流量停止扩大并触发回滚。恢复旧摘要后读取原会话、查询课程、完成一次流式问答；记录发现、决策、命令、耗时和改进项。

## 关键代码与配置

下面的 Dockerfile 使用专用用户并提供健康检查。示例不包含密钥；运行平台在启动时注入已批准的配置。

```dockerfile
FROM python:3.12-slim AS runtime
ENV PYTHONDONTWRITEBYTECODE=1 PYTHONUNBUFFERED=1
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt \
    && useradd --system --uid 10001 appuser
COPY --chown=appuser:appuser . /app
USER appuser
EXPOSE 8000
HEALTHCHECK --interval=30s --timeout=3s --retries=3 \
  CMD python -c "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8000/health/live')"
CMD ["uvicorn", "backend.app:app", "--host", "0.0.0.0", "--port", "8000"]
```

生产构建应进一步锁定基础镜像摘要并使用依赖哈希。Docker `HEALTHCHECK` 只能表达单一容器状态；编排平台通常分别配置 startup、liveness 和 readiness 探针。

## 调试和常见故障

### 故障一：容器显示 healthy，课程请求仍持续失败

**现象：** 平台探针一直为绿色，所有课程问答却返回索引未就绪。**原因：** 健康检查只访问根路由或确认进程端口开放，没有区分 liveness 与 readiness；流量在索引准备前进入。**定位：** 比较探针路径、课程索引状态和请求时间线，检查实例何时加入负载均衡。**修复：** 保留轻量 liveness，新增反映关键本地资源的 readiness；首次索引由受控任务构建，ready 后才接流量，并为构建失败提供终态和重试而非无限等待。

### 故障二：镜像回滚成功但旧版无法读取会话

**现象：** 部署平台已切回上一镜像摘要，历史学习页面报数据格式错误。**原因：** 新版启动时原地升级了会话 schema，迁移不可逆且发布前没有备份或兼容读取。**定位：** 检查数据文件版本、迁移记录和回滚时间点，在副本中验证旧程序读取备份。**修复：** 对格式变化采用向后兼容写入、双读或可逆迁移；发布前备份并验证恢复，回滚手册同时指定镜像与数据步骤，将会话恢复加入冒烟测试。

## 安全、成本与职业规范提示

镜像和流水线拥有供应链权限，构建日志、缓存与制品仓库都可能泄露凭据。密钥只在需要的运行步骤短期可用，流水线权限最小化，第三方 Action 或基础镜像要固定版本并审查来源。扫描发现高危漏洞应按可利用性和环境评估，但不能静默忽略；例外必须有期限与负责人。

资源限制防止单个实例耗尽主机，也要避免限制过低造成频繁重启。预留优雅停机时间会占用发布容量，应纳入滚动策略。课程索引是可重建制品，用户会话和确认记录是业务数据，两者备份等级不同。不要为了节省存储把所有数据塞入容器可写层。

发布人员必须保留制品和审批链，现场修复也应回到代码库和流水线，不在生产容器内手改后遗忘。回滚不是失败，而是风险控制动作；复盘关注探针、门禁和兼容性为何未提前发现问题，并把教训转成自动检查。

## 实训练习

为 AstraMentor 类 FastAPI 服务编写容器化方案，列出构建上下文排除项、非 root 权限、运行配置、持久目录和三类探针语义。在干净环境启动镜像，验证缺少必需配置时快速失败但不打印敏感值；验证课程索引 stale 时实例不承担课程流量，而普通存活检查仍成功。

设计一条持续交付流水线，至少包含 Python 测试、课程材料校验、镜像构建、依赖扫描、测试部署和冒烟。随后发布一个故意使 readiness 失败的候选版本，执行回滚并验证历史会话、课程列表和流式问答。进阶练习要求记录镜像摘要和一次备份恢复的 RTO 实测值。

## 本项目小结

工程化部署把源代码转化为可重复运行、可验证和可恢复的服务。安全镜像、运行时配置、非 root 权限、明确存储边界和不可变摘要构成制品基础；startup、liveness、readiness 与优雅停机让编排平台正确管理生命周期；持续交付门禁确保只有经过验证的制品进入环境。

可靠发布还要求数据兼容和真实回滚演练。切回旧镜像并不等于服务恢复，必须验证课程、会话、配置和关键业务路径。前七个项目分别建立了质量、测试、评测、观测、安全、性能和部署能力，下一综合项目将把它们串成一次完整的上线验收。
