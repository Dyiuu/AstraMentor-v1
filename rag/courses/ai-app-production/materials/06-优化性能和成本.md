# 项目六：优化 AI 应用性能与成本

## 岗位情境

职业学习 Agent 在试用周迎来集中实训，上午九点同时在线人数迅速上升。监控显示平均延迟尚可，P95 完整响应超过三十秒，部分学生重复点击导致同一问题生成三次；长对话把全部历史反复发送给模型，单位完成任务 Token 比预估高出四倍。团队有人建议统一换最快、最便宜的模型，也有人想增加无限重试，可能牺牲回答质量、安全检查和费用可控性。

你作为 AI 性能工程师，要在已建立的质量和安全门禁下优化整个请求链。目标不是追求单个数字最小，而是让学生在可接受时间内完成任务，并使每个成功任务的资源消耗可预测。你需要测量排队、检索、模型首字、生成、工具和持久化各阶段，建立容量模型，依次减少无效工作、控制上下文、设置并发与超时，再谨慎使用缓存、路由和降级。

优化必须用真实负载与质量回归证明。首字变快但最终答案缺少引用，费用下降但误拒答上升，都不能称为成功。任何缓存和合并请求还需保持用户、课程与权限隔离。

## 项目目标

完成本项目后，你应能建立性能与成本基线，理解首字延迟、总延迟、吞吐、并发、排队时间和分位数的关系，按完成任务计算 Token 与工具费用。你应能设计 Token 预算、历史摘要、超时预算、有限重试、背压、并发限制、缓存和模型路由，并通过压测与效果评测确认优化没有突破质量安全门禁。

项目达成标准是：在给定负载下，核心 SLO 达标，单位成功任务成本下降，错误与质量指标不退化；达到容量上限时系统明确排队、限流或降级，不出现无限等待、重试风暴和跨用户缓存泄露。

## 项目产物与验收条件

输入包括生产 trace、延迟与 Token 指标、模型价格配置、任务分层、质量门禁、目标并发和供应商限额。输出包括基线报告、阶段耗时分解、Token 预算、容量模型、优化实现、压测脚本、质量回归和成本对比。验收证据需包含同一负载与同一数据集上的优化前后结果。

- 报告同时展示 P50、P95 首字延迟和总延迟，不只展示平均值。
- 成本分母为成功完成的学习任务，并包含重试、检索、模型和工具调用。
- 每个外部依赖具有连接、首字或读取、总耗时和重试上限。
- 并发超过容量时启用背压或明确 429，不无限创建任务。
- 缓存键包含权限与课程作用域，不缓存高敏感或高副作用结果。
- 优化后运行固定质量、安全回归，所有阻断项仍通过。

输入数据应按模型、课程和任务类型切片。输出必须说明测试硬件、负载模型、样本版本和测量窗口，否则无法公平比较。

## 任务分析

优化顺序遵循“测量—消除浪费—设置边界—改变架构—验证”。先从 trace 找出主要耗时和费用，再删除重复调用、无用上下文和无效重试；随后给并发、队列和超时设上限；最后才考虑模型路由、缓存、批处理等复杂手段。每次只改变少量变量，用相同压测和质量集验证，便于归因。

### 优化假设记录

每项改动先写假设，例如“重复点击占模型请求的 12%，按会话与幂等键合并可降低成本且不影响答案”。为假设指定观测指标和停止条件。结果不支持假设时撤回，不要把偶然波动解释为成功。

## 核心知识

### 延迟分解与容量

端到端延迟包括客户端上传、网关排队、检索、模型排队、首个 Token、持续生成、工具调用和状态写入。流式输出改善感知等待，但不一定缩短总工作量，因此要分别度量首字与完成。平均值对长尾不敏感，P95、P99 更能反映集中实训时的体验。排队时间快速增长通常表示服务接近容量上限。

可用 Little 定律的直觉理解并发：系统内平均任务数约等于到达率乘平均停留时间。若模型请求平均十秒、每秒到达五个，稳定状态就需要约五十个在途槽位；供应商限额或连接池小于需求时必须排队。队列需要最大长度、等待超时和拒绝策略，不能把内存当作无限缓冲。

### Token 与任务成本

成本由输入、输出、Embedding、重排、工具和失败重试共同组成。长历史的边际价值会下降，可以保留最近交互、结构化学习状态与经验证摘要；系统提示和工具定义也要去重。Token 预算按任务风险和复杂度设置，达到上限时优先压缩冗余，再选择明确截断或让用户缩小问题，不能静默删除关键安全约束。

成本应按成功任务和质量合格任务观察。廉价模型若造成更多重试、人工复核或错误工具调用，实际总成本可能更高。模型路由先用确定特征分类：任务风险、是否需要视觉、上下文长度、结构化输出和工具能力；高风险或能力不匹配时不能为了省钱降级。

### 缓存、重试与降级边界

缓存适合稳定、只读、权限清晰的结果，例如教材索引状态和公共课程片段。生成答案语义缓存可能返回过期或不属于当前课程的内容，键必须包含课程、资料版本、权限和提示版本，敏感问答默认不共享。缓存命中也要保留来源与生成版本，教材更新后主动失效。

重试只适合临时且可能恢复的错误，并要求幂等。指数退避加随机抖动可以避免客户端同时重试；总次数与总时长必须受请求预算限制。模型生成中途断开不一定适合自动重试，因为可能重复计费或重复工具动作。降级顺序可为减少候选检索、关闭非关键美化、切换兼容模型、返回可重试提示，但安全校验和课程隔离不能降级。

## 工程实现步骤

### 步骤一：采集基线并定位瓶颈

使用固定负载运行十五分钟，记录每阶段 span、在途数、队列长度、Token 和成功任务。按简单问答、RAG 问答和工具任务切片，画出延迟瀑布与成本构成。选出贡献最大的两个瓶颈，不凭单次本地调用判断。

### 步骤二：设置预算和请求边界

为每类任务定义输入 Token、输出 Token、总时长和工具次数预算。实现连接超时、首字超时与总超时，重试共享同一总预算。对重复点击生成幂等键，在相同会话与请求仍进行时返回同一任务状态。设置连接池、并发信号量和有界队列。

### 步骤三：减少无效工作并实施路由

压缩重复系统文本，历史改为最近消息加结构化摘要；检索先过滤课程与元数据，再重排有限候选。依据任务能力矩阵选择模型，不使用模型自报能力。只对低风险只读结果实施缓存，键包含资料与提示版本，并配置失效策略。

### 步骤四：压测、回归并确定容量

使用阶梯负载逐步增加到达率，观察 P95、错误率、队列和成本拐点。超过目标后验证背压是否明确，恢复后队列是否排空。对优化版运行同一效果与安全集，检查引用、拒答和工具权限。最终给出建议容量、扩容触发点和剩余瓶颈。

## 关键代码与配置

下面示例以信号量限制模型并发，并把排队等待纳入总预算。生产实现还应记录队列指标，并将超时映射为可理解的错误。

```python
import asyncio

class ModelLimiter:
    def __init__(self, concurrency=20):
        self.slots = asyncio.Semaphore(concurrency)

    async def run(self, client, request, total_timeout=18):
        async def bounded():
            async with self.slots:
                return await client.generate(request)
        return await asyncio.wait_for(bounded(), timeout=total_timeout)

async def generate_with_budget(limiter, client, request):
    if request.estimated_tokens > request.token_budget:
        raise ValueError("token_budget_exceeded")
    return await limiter.run(client, request)
```

信号量不能解决供应商每分钟 Token 限额，实际系统还需速率桶和队列策略。超时后要取消底层任务并确认工具没有继续执行，避免用户已收到失败而后台仍产生费用。

## 调试和常见故障

### 故障一：加入重试后成功率下降且费用上升

**现象：** 供应商限流时每个请求自动重试三次，队列持续增长，单位成功任务费用翻倍。**原因：** 所有客户端同步立即重试，重试占据并发槽位并放大限流；总预算没有包含等待时间。**定位：** 在 trace 中统计每任务尝试次数、退避时间和状态码，观察重试与队列长度的时间相关性。**修复：** 只重试明确的临时错误，采用指数退避和随机抖动，限制总尝试与总时长；结合全局限流和断路器，在依赖不可用时快速降级。

### 故障二：缓存命中率提高但出现跨课程答案

**现象：** 相同问题在两门课程中得到同一引用，成本下降但课程隔离门禁失败。**原因：** 缓存键只使用规范化问题文本，未包含课程 ID、索引版本和权限范围。**定位：** 从响应缓存键反查生成上下文，比较命中请求的课程与资料版本；运行两课程同主题负向测试。**修复：** 缓存键加入课程、索引哈希、提示版本和授权范围，对个性化或敏感答案禁用共享缓存；教材变更时失效对应课程，并将跨课用例加入发布阻断集。

## 安全、成本与职业规范提示

性能优化不得删除权限检查、输入校验、人工确认和审计。为降低延迟绕过安全层，或在不同用户间共享敏感缓存，属于不可接受的工程行为。压测必须使用隔离账户与假工具，设置最大调用预算，避免对供应商或学校网络造成真实拒绝服务。

价格与能力可能变化，费用配置需要版本和核验时间，报告不得承诺永久固定单价。压测结果受硬件、地区、模型负载和样本长度影响，应记录环境并说明外推限制。发现成本异常要从任务链分析，不将压力简单转嫁为无限缩短学生答案。

工程师应公开优化的取舍。若为达到 SLO 降低了候选数或输出长度，必须由效果评测证明关键能力未退化；若容量不足，应明确限流和扩容计划，而不是让请求无提示地等待。容量报告是运营决策证据，不是营销峰值数字。

## 实训练习

为一个 RAG 学习服务设计三类负载：简单问答、带引用问答和只读工具查询。以阶梯方式从每秒一请求增加到八请求，记录首字 P50/P95、总延迟 P95、队列、错误率、Token 和单位成功任务成本。根据 trace 找出两个主要瓶颈，并写出可证伪的优化假设。

实现并发限制、总超时和重复请求去重，再选择历史压缩或权限隔离缓存之一。使用相同负载复测，并运行课程隔离、引用和工具安全回归。进阶练习要求故意注入供应商 429，比较立即重试与带抖动退避对队列和成本的影响。

## 本项目小结

AI 性能与成本优化是一项端到端工作。只有拆分排队、检索、首字、生成、工具和持久化，才能找到真实瓶颈；只有按成功任务计算费用，才能看见重试与失败的浪费。先消除重复工作并设置预算边界，再考虑缓存、路由和架构改变，能够降低复杂度和风险。

每次优化都要用同负载、同样本和质量安全回归验证。背压、有限重试与明确降级让系统在容量不足时保持可预测。下一项目会把这些运行边界装入容器、健康检查与持续交付流程，形成可部署、可回滚的生产服务。
