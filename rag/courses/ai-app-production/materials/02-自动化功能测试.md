# 项目二：建设 AI 应用自动化功能测试

## 岗位情境

质量标准已经确定，团队需要把“每次提交都能检查”的要求落到代码上。当前职业学习 Agent 由模型客户端、RAG 检索器、工具路由、会话状态和 FastAPI 接口组成。开发人员手工点击页面时功能正常，但更换模型配置后，工具参数缺少 `course_id`；修复这一问题又导致流式接口在异常时留下空消息。由于测试依赖真实模型，执行一次要等待数分钟，结果还会随网络和模型输出变化，大家逐渐不愿运行回归。

你作为 AI 测试工程师，需要建立一套快速、确定、可定位的自动化测试。重点不是证明模型“永远正确”，而是验证应用自己能够控制的契约：请求怎样构造，工具是否经过参数校验，课程索引未就绪时是否阻断模型调用，流式事件是否符合协议，失败是否按设计降级，状态是否被正确保存。开放式语义质量留给下一项目，本项目聚焦可重复的软件行为。

最终测试必须能在没有外网、没有真实密钥、没有真实副作用的环境运行。它应把模型、检索服务和外部工具替换为受控测试替身，同时保留少量跨组件集成测试，防止所有单元各自正确却无法协作。

## 项目目标

完成本项目后，你应能依据系统边界设计测试金字塔，区分 stub、fake、mock 和 contract test 的用途，为非确定模型建立确定性替身，并使用依赖注入观察“模型是否被调用”等关键副作用。你还应能测试同步接口、流式 SSE、工具参数、超时重试、幂等更新和课程作用域隔离。

岗位能力的判断标准是：修改一个接口字段、删除一次权限检查或改变事件顺序时，测试能给出明确失败；模型供应商暂时不可用时，大部分测试仍在本地完成；失败信息能够指向具体契约，而不是笼统报告“生成结果不一致”。

## 项目产物与验收条件

项目输入包括接口定义、质量门禁、关键业务路径、依赖清单和已知缺陷。输出包括自动化测试目录、测试替身、固定样本、覆盖矩阵、执行脚本与测试报告。验收证据由测试日志、失败演示记录、覆盖矩阵和一次干净环境执行截图组成。

- 至少覆盖模型客户端、工具层、RAG 护栏、会话状态和 HTTP 接口五个边界。
- 全部核心测试在断网且不设置真实 API 凭据时可运行。
- 至少演示一个缺陷注入：移除保护条件后测试失败，恢复后重新通过。
- 流式测试验证事件类型、顺序、结束标记与异常路径，不只拼接正文。
- 工具测试断言未经授权的参数不会触发真实执行函数。
- 报告区分快速单元测试、组件测试和少量端到端冒烟测试。

建议目录为 `tests/unit/`、`tests/component/`、`tests/contract/`、`tests/fixtures/` 和 `tests/fakes/`。测试命名应表达场景与期望，例如 `test_stale_course_index_blocks_model_call`，避免使用无法解释行为的编号。

## 任务分析

先画出一次学习请求经过的组件和副作用：读取状态、检索证据、调用模型、执行工具、写回进度、返回事件。将纯函数和可控边界放入单元测试，将序列化、文件与 HTTP 组合放入组件测试，将真实进程启动但仍使用假模型的路径放入冒烟测试。对每个高风险规则至少安排一个正例和一个反例。

### 测试优先级

优先自动化高频、可确定、失败损害大且人工重复成本高的行为。模型回答文风不适合逐字断言，课程身份、JSON Schema、工具权限、错误码和状态持久化则非常适合。若某行为只能通过真实供应商验证，应把它标为外部兼容性测试，设置低频执行和清晰跳过原因，不能让它拖慢每次提交。

## 核心知识

### 测试替身的选择

Stub 返回预设结果，适合模拟模型生成或检索列表；fake 具有简化但真实的行为，例如内存会话仓库；mock 关注交互，适合断言高风险情况下工具或模型从未被调用。替身不是越多越好，过度模拟内部方法会让重构导致大量无价值失败。优先在稳定边界替换依赖，例如统一模型客户端、工具执行器和课程 Retriever。

确定性假模型可以按输入标签返回结构化内容、流式分片或指定错误。它不需要理解自然语言，但必须支持正常、超时、限流、无效 JSON、工具请求和流中断等协议情形。每个返回场景都应有名字，测试读取名字而不是在代码里散落长文本。

### 断言 AI 应用契约

好的断言观察业务可见行为。对于 RAG 课程模式，应断言未就绪返回结构化 409、错误中包含原课程 ID、模型调用次数为零；对于工具调用，应断言工具名在允许列表、参数通过模式校验、危险操作等待确认；对于会话，应断言更新后课程身份不变。不要断言私有辅助函数调用顺序，除非该顺序本身就是安全契约。

流式响应需要按事件解析。至少验证 `meta` 在正文之前、多个 `content_delta` 可以安全拼接、独立 reasoning 不混入可见答案、错误事件带请求 ID、完成时存在 `done`。还要覆盖客户端取消：服务端停止后不得提交未完成教学内容，资源应被释放。

### 分层、隔离与可维护性

单元测试追求毫秒级和故障定位；组件测试允许临时目录、真实 JSON 序列化和 ASGI 路由；端到端测试验证最小主路径，不承担所有边界。文件测试使用每个用例独立的临时目录，环境配置在测试结束后恢复，时间和随机数通过注入固定。测试之间若共享可变单例，单独运行可能通过、全量运行却失败，这是典型污染。

回归样本需要稳定 ID 和缺陷来源。修复问题时先写能复现的失败测试，再实现修复，并把测试关联到风险或工单。覆盖率只能说明哪些代码被执行，不能说明断言是否有效；因此要用缺陷注入或变异思路检查测试是否真的会“看见”关键保护被删除。

## 工程实现步骤

### 步骤一：定义依赖接口和测试替身

列出模型生成、检索、工具执行、时钟和存储五类边界，为每类定义最小协议。实现可配置假模型，记录接收到的参数与调用次数；实现内存工具执行器，只返回模拟结果，不访问网络或业务数据库。保证替身能主动抛出超时、无效响应和权限错误。

### 步骤二：编写核心单元与护栏测试

从发布阻断项开始：未知课程不能进入路径、索引未就绪不能调用模型、工具参数越权不能执行、状态更新不能改变课程身份。每个测试遵循“准备—执行—断言”，只验证一个主要行为，并在断言消息中说明风险。使用参数化覆盖 missing、stale、building 和 failed 等等价状态。

### 步骤三：编写 HTTP 与流式契约测试

在进程内启动 ASGI 应用，替换外部依赖，向路由发送真实 JSON。检查状态码、Content-Type 和 FastAPI 外层 `detail` 结构。对流式接口逐个解析 SSE 事件，覆盖正常完成、模型异常和客户端取消；不要只把响应当成普通字符串搜索。

### 步骤四：组织执行层级和故障注入

为本地提交、持续集成和候选发布分别配置测试集合。暂时删除一次课程 ready 检查或把危险工具加入默认允许列表，确认对应测试准确失败并能指出原因。恢复代码后全量运行，记录总耗时、隔离性和不稳定用例；不稳定测试必须修复根因，不能简单无限重试。

## 关键代码与配置

下面示例使用一个记录调用次数的假模型，验证索引未就绪时应用在进入生成层之前停止。真实项目可以通过构造参数或应用依赖覆盖注入替身。

```python
class FakeModel:
    def __init__(self):
        self.calls = 0

    def generate(self, prompt):
        self.calls += 1
        return "受控测试回答"

def test_stale_index_blocks_generation(client, fake_model):
    response = client.post(
        "/api/learning/chat",
        json={"topic": "工具系统", "course_id": "demo-course",
              "node_name": "参数校验", "question": "如何校验？"},
    )
    assert response.status_code == 409
    assert response.json()["detail"]["code"] == "course_index_not_ready"
    assert fake_model.calls == 0
```

对于流式测试，可先把 SSE 解码成事件对象，再断言类型序列。测试替身返回短小分片和确定请求 ID，避免逐字输出差异影响契约检查。任何需要真实密钥的测试都不属于默认自动回归集。

## 调试和常见故障

### 故障一：单独运行通过，全量运行随机失败

**现象：** 某个会话测试单独执行稳定，通过全套测试时偶尔读到另一课程的数据。**原因：** 用例复用了全局 registry、固定状态文件或环境变量，前一个测试留下的对象改变了后一个测试的初始条件。**定位：** 打乱测试顺序并记录临时路径、单例 ID 和环境差异；用二分方式缩小会互相影响的用例组合。**修复：** 为文件和索引使用独立临时目录，为单例提供可注入实例，在清理阶段恢复环境；禁止测试依赖执行顺序，并增加两课程同主题的隔离断言。

### 故障二：模型明明没有被调用，mock 断言却失败

**现象：** HTTP 已返回 409，但测试显示模型客户端构造或方法发生一次调用。**原因：** 护栏设置在服务创建之后，而服务构造函数立即初始化了远程客户端；或者 mock 放在了错误导入位置。**定位：** 查看调用栈和 patch 目标，区分“构造对象”和“执行生成”；确认路由实际引用的是哪个模块中的名字。**修复：** 把课程身份与索引检查前移到创建生成服务之前，远程依赖改为延迟初始化；在使用方命名空间注入替身，并分别断言构造和生成行为。

## 安全、成本与职业规范提示

测试环境不应连接真实生产工具。发送通知、创建工单、删除数据和支付等副作用必须由 fake 执行器承接，即便测试输入声称“这是演练”也不能放宽。固定样本中的个人信息应匿名化，日志断言只检查脱敏字段。不要把密钥写进 fixture，也不要为通过测试关闭证书验证或权限校验。

默认回归应快速稳定，使开发人员愿意频繁运行。把昂贵模型兼容性测试分离到受控任务，设置预算和调用上限，并缓存只读的供应商能力结果。发现失败时保存必要请求元数据，不保存完整隐私对话。测试报告必须如实列出跳过项和外部依赖不可用，不能把“未运行”呈现为“通过”。

职业测试人员需要尊重实现边界又保持独立判断。不要为了提高覆盖率编写永远为真的断言，也不要用重复重跑掩盖竞态。测试失败的价值在于提前提供可操作证据，命名、日志和最小复现都属于交付质量的一部分。

## 实训练习

为一个包含课程 RAG 和工具调用的 FastAPI 服务设计不少于十五个自动化用例。至少覆盖四种索引非就绪状态、未知课程、检索空结果、工具参数错误、危险工具确认、模型超时、流式完成、流式取消、会话保存和两课程同主题隔离。使用假模型和临时目录执行，记录每个用例对应的风险 ID。

然后实施一次缺陷注入：把“索引未就绪时阻断”移动到服务创建之后，运行测试并解释哪一条断言捕获了额外模型初始化；再恢复正确实现。进阶任务是编写一个流式事件解析辅助函数，让测试能报告第一个不符合顺序的事件，而不是只提示整段字符串不相等。

## 学习评价量表

| 评价维度 | 优秀（90—100） | 合格（60—89） | 需改进（60以下） | 权重 |
|---|---|---|---|---:|
| 测试分层 | 单元、组件、契约边界清楚 | 覆盖主要层级 | 全部依赖真实模型或仅有手测 | 15% |
| 测试替身 | 能模拟成功、错误与流式场景 | 有基本假模型 | 替身不可控或产生真实副作用 | 20% |
| 核心契约 | 高风险护栏均有正反例 | 主要接口有断言 | 只检查状态为成功 | 25% |
| 隔离与稳定 | 断网可运行且无顺序依赖 | 大部分测试稳定 | 污染文件、环境或频繁随机失败 | 20% |
| 缺陷检出 | 缺陷注入能准确失败并定位 | 能发现一个真实回归 | 删除保护后测试仍通过 | 10% |
| 报告规范 | 覆盖矩阵、跳过项和证据完整 | 有执行结果 | 隐瞒未运行或日志不可读 | 10% |

若测试调用真实高影响工具、提交真实凭据或以无限重试掩盖不稳定，即使其他项得分较高也不能通过职业安全验收。

## 本项目小结

AI 自动化功能测试的核心，是把应用可以控制的行为从模型开放性中分离出来。通过稳定边界、确定性测试替身和分层测试，可以快速验证课程身份、RAG 护栏、工具权限、状态持久化与流式协议。开放式回答不适合逐字快照，但生成前后的工程契约完全可以严格检查。

一套可信的回归不仅要通过，还要证明关键缺陷出现时会失败。断网执行、临时资源隔离、明确跳过项和缺陷注入，使测试从“展示代码跑过”变成发布证据。下一项目将在这一可靠功能底座上，进一步评价答案相关性、依据忠实度和任务完成效果。
