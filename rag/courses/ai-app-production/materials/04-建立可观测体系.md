# 项目四：建立 AI 应用可观测体系

## 岗位情境

职业学习 Agent 已通过离线评测并开始小流量试用。教师反馈某些夜间请求会等待很久，学生只看到“正在思考”；运维面板显示 HTTP 200，无法说明时间消耗在检索、模型首字、工具调用还是状态写入。另一次回答引用错误，开发人员只有最终文本，没有当时的课程 ID、检索片段和版本信息，问题无法复现。团队积累了大量日志，却仍要靠猜测定位故障。

你作为 AI 应用运维工程师，需要建立以请求为主线的可观测体系。系统要把网关、RAG、模型、工具、会话与流式传输连接成一条 trace，用指标观察服务水平，用结构化日志保留可审计事件，同时控制隐私、基数和存储成本。目标不是“记录所有内容”，而是在不泄露学生数据的前提下回答：哪类请求失败、失败发生在哪个环节、影响多少用户、从哪个版本开始、是否触及服务目标。

AI 应用的可观测性还要区分技术成功与任务成功。HTTP 200 可能包含拒答、空引用或工具失败；模型总延迟正常，首个可见内容却很慢。因而需要将传统基础设施信号与模型、检索、工具和业务结果共同建模。

## 项目目标

完成本项目后，你应能解释日志、指标与分布式追踪的互补关系，为 AI 请求设计稳定的 trace/span 层次和低基数字段，采集首字延迟、总延迟、Token、检索命中、工具错误与课程作用域等信号。你还应能够定义面向用户的 SLI/SLO，配置多窗口告警，使用 trace ID 从告警下钻到根因，并设计采样、脱敏和保留策略。

合格产物应支持一次盲测排障：给出某个告警和请求 ID，另一名同学无需查看源代码即可判断慢点或错误组件，并找到相关版本与非敏感上下文；同时，观测系统自身不能把完整提示、密钥或个人信息暴露在日志中。

## 项目产物与验收条件

项目输入包括服务拓扑、接口协议、质量标准、隐私分级、预估流量和一次历史故障。输出包括遥测字段字典、trace 设计、指标与 SLO、结构化日志规范、告警规则、仪表板草图和一次故障演练报告。验收证据包含可关联的 trace、指标截图或导出数据、脱敏日志和告警到根因的时间线。

- 一次请求在网关、检索、模型、工具和状态环节共享同一 trace 上下文。
- 至少采集请求量、错误率、首字延迟、总延迟和单位任务成本五类指标。
- 课程 ID、模型版本和结果状态可用于合理切片，用户输入不作为指标标签。
- 日志中不出现完整密钥、个人身份、完整系统提示或未脱敏对话。
- 告警绑定明确 SLO、窗口、严重度、负责人和排障入口。
- 使用注入的模型超时完成一次演练，并在十分钟内定位责任 span。

输入和输出都必须注明版本。若仪表板只有平均延迟，或 trace 无法连接日志与指标，则不满足验收要求。

## 任务分析

先从用户旅程确定关键阶段和成功定义，再设计 trace 结构；随后从质量标准选择少量 SLI，确定标签、窗口与目标；接着定义结构化日志事件和脱敏规则，最后布置告警并通过故障注入验证。遥测设计要先考虑问题，再考虑字段，避免“能采什么就采什么”造成噪声和高成本。

### 观测问题清单

设计前至少写出十个需要回答的问题，例如“P95 首字延迟升高发生在哪个模型”“引用为空是否集中在一门课程”“工具失败后是否正确降级”“哪个版本开始重复提交”。每个字段必须服务于一个问题或审计义务；无法说明用途的高敏感字段不应采集。

## 核心知识

### 三类信号与关联

指标是时间窗口内的数值聚合，适合发现趋势和触发告警；日志记录离散事件和上下文，适合审计与解释；trace 描述一次请求经过的多个 span，适合分析端到端因果和并行耗时。三者用 `trace_id`、`span_id`、服务名和版本关联：指标发现异常，代表 trace 展示慢点，结构化日志补充错误类别。

推荐的 span 层次包括 `http.request`、`rag.retrieve`、`llm.generate`、`tool.execute` 和 `state.persist`。每个 span 记录开始、结束、状态和少量稳定属性。模型 span 可以记录供应商、模型别名、输入输出 Token 数与首字时间，但不默认记录完整提示；检索 span 记录课程 ID、top_k、命中数和索引版本，必要时只保存引用 ID；工具 span 记录工具名、授权结果和错误类别，不记录敏感参数原值。

### 指标、标签与服务目标

用户可感知的 SLI 比 CPU 使用率更接近可靠性，例如“成功完成且在十五秒内返回首个内容的学习请求比例”。延迟使用直方图和分位数观察长尾；错误率区分业务拒答、客户端错误、依赖错误和内部错误。Token 与费用按任务聚合，避免多次重试被遗漏。

标签必须低基数。课程 ID、路由、状态、模型别名和工具类别通常可控；用户 ID、问题文本、trace ID 和完整错误消息会产生高基数，不能成为指标标签。高基数信息可以进入受限日志或 trace。SLO 应设置目标窗口和错误预算，例如滚动二十八天的成功率，而告警采用快慢两个窗口，既发现突发故障，也捕获持续缓慢消耗。

### 采样、脱敏与观测系统可靠性

全量保留 trace 成本较高，可以对成功请求比例采样，对错误、高延迟和高风险工具请求提高保留率。尾部采样在请求结束后根据状态决定，信息更完整，但需要缓冲资源。采样规则必须版本化，否则前后趋势难比较。

脱敏应在遥测进入共享后端前完成。字段分为公开、内部、敏感和禁止记录四级；密钥、密码、完整身份和系统提示属于禁止记录。对问题文本可使用长度、语言、风险标签或不可逆摘要替代。遥测导出失败不能阻断主业务，但必须有自身健康指标和有限缓冲，避免无限占用内存。

## 工程实现步骤

### 步骤一：定义 span 拓扑和传播规则

从 HTTP 入口创建根 span，把上下文传播到检索、模型和工具客户端。统一命名、状态与错误分类，异步任务显式传递上下文。用一个包含并行检索与模型流的请求验证父子关系和时间轴，确认取消时所有子 span 正确结束。

### 步骤二：实现结构化遥测字段

建立字段白名单和敏感级别，在公共中间件记录路由、版本、课程 ID 和请求结果。模型、Retriever 与工具分别补充领域字段。异常转换为稳定错误码，原始堆栈只进入访问受限的诊断通道。为脱敏函数编写单元测试，覆盖 Token、邮箱和工具参数。

### 步骤三：建立指标、SLO 与仪表板

从质量标准选择用户成功率、首字延迟、总延迟、检索空结果率、工具错误率和单任务成本。定义单位、分母与标签，制作总览、RAG、模型、工具四组面板。为核心 SLO 配置快慢窗口告警，并在告警描述中加入仪表板和 trace 查询入口。

### 步骤四：执行故障注入演练

让假模型延迟、Retriever 返回空结果、工具抛出超时，分别观察指标、trace 和日志。记录告警出现时间、定位步骤、根因和恢复验证。若只能通过查看应用控制台找到原因，说明关联字段或 span 边界仍不完整，应修订后再次演练。

## 关键代码与配置

以下 Python 片段展示在模型调用周围创建 span，并只写入允许的元数据。具体 SDK 初始化和导出器由部署环境统一配置。

```python
from opentelemetry import trace

tracer = trace.get_tracer("ai.learning")

def call_model(client, prompt, course_id):
    with tracer.start_as_current_span("llm.generate") as span:
        span.set_attribute("ai.course_id", course_id)
        span.set_attribute("ai.model", client.model_alias)
        span.set_attribute("ai.prompt_chars", len(prompt))
        try:
            result = client.generate(prompt)
            span.set_attribute("ai.output_chars", len(result))
            return result
        except Exception as exc:
            span.record_exception(exc)
            span.set_status(trace.StatusCode.ERROR)
            raise
```

代码没有把 `prompt` 本身写入 span。若业务确需保存样本，应走独立、受控、可删除的数据管道，而不是临时把敏感正文塞入通用日志。

## 调试和常见故障

### 故障一：指标告警升高却找不到对应 trace

**现象：** 仪表板显示模型错误率突然升高，按时间查询 trace 几乎没有失败样本。**原因：** 统一概率采样丢弃了大部分请求，未对错误状态执行尾部保留；或者指标与 trace 使用了不同的服务版本标签。**定位：** 检查 Collector 采样规则、导出计数和资源属性，使用一个固定错误请求观察各阶段是否产生并导出 span。**修复：** 对错误、长延迟和高风险操作设定高优先级尾部采样，统一资源字段；为“产生 span 数—接收数—导出数”建立自监控指标。

### 故障二：监控费用暴涨且查询变慢

**现象：** 新增课程问答面板后时序数量快速增长，指标后端查询超时。**原因：** 将问题文本、用户 ID 或 trace ID 作为指标标签，产生近乎每请求唯一的高基数序列。**定位：** 统计各标签基数和新增序列来源，检查最近字段变更；对比删除可疑标签后的基数。**修复：** 指标只保留课程、状态、路由等受控标签，高基数值移入采样日志或 trace；为遥测字段变更增加评审和基数预算测试。

## 安全、成本与职业规范提示

可观测数据不是“内部就可以随意看”。它可能重建学生学习轨迹、暴露系统提示、工具参数和教材片段，必须设置访问角色、保留期限、导出审计和删除流程。调试开关不能在生产长期记录完整对话；发生事故时临时提高采样也要有审批、范围和自动到期。

观测成本由事件量、属性大小、基数、采样率和保留时长共同决定。先保存能够支持 SLO 与根因分析的字段，再依据真实查询补充；压缩和批量导出要设置上限，遥测后端不可用时优先保护主服务。禁止为了减少费用删除全部错误证据，也禁止为了“以后可能有用”无限留存敏感内容。

运维报告应使用稳定错误码而非把用户问题当作分类标签。排障人员访问敏感 trace 要有工作需要，并在工单中记录用途。将故障复盘聚焦系统和流程改进，不用遥测数据对个别学生或员工做无依据评价。

## 实训练习

为一个包含 RAG、流式模型与工具调用的服务设计 trace 拓扑，列出每个 span 的允许属性、禁止属性和错误状态。定义六个指标，其中至少包含首字延迟、课程检索空结果率、工具错误率和单位完成任务 Token。选择一个用户导向 SLO，说明分母、目标窗口与错误预算。

随后使用假依赖注入三类故障：模型延迟八秒、检索返回空结果、工具超时。要求从告警进入仪表板，再选择代表 trace 定位根因，并写出不超过十步的排障记录。进阶练习是比较 100% 头部采样与错误优先尾部采样在证据完整度和成本上的差异。

## 学习评价量表

| 评价维度 | 优秀（90—100） | 合格（60—89） | 需改进（60以下） | 权重 |
|---|---|---|---|---:|
| Trace 设计 | 链路完整、状态清晰且支持取消 | 覆盖主要组件 | span 孤立或无法定位耗时 | 25% |
| 指标与 SLO | 面向用户、口径明确、可告警 | 有核心技术指标 | 只有平均值或无分母 | 20% |
| 日志关联 | 结构化并能从 trace 下钻 | 有基本请求关联 | 依靠无结构控制台文本 | 15% |
| AI 领域信号 | 覆盖检索、模型、工具和成本 | 覆盖两类 AI 信号 | 只有 CPU 与 HTTP 200 | 15% |
| 隐私与成本 | 脱敏、采样、基数和保留合理 | 有基本保护 | 记录完整提示或高基数失控 | 15% |
| 故障演练 | 告警到根因证据完整 | 能定位主要故障 | 无法关联或没有恢复验证 | 10% |

若日志包含真实敏感凭据、未脱敏身份或完整系统提示，项目直接判定不通过，并要求清除测试数据与复核访问记录。

## 本项目小结

可观测性让团队从系统外部提出新问题，并通过指标、trace 和日志找到证据。AI 应用需要在传统请求链路上增加检索、模型、工具、Token、首字延迟和业务结果信号，同时避免把高敏感正文变成普通遥测。稳定命名、上下文传播和低基数标签是关联分析的基础。

可靠体系必须经过故障注入验证，而不是以“已经接入 SDK”作为完成。告警应连接 SLO 和排障入口，采样应优先保留高价值失败，遥测自身也需要健康监测。下一项目将利用这些可追溯信号，验证提示注入、越权工具和敏感数据等安全风险的防御效果。
